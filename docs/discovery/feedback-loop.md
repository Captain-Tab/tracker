# 闭环反馈体系：影子跟踪 / 预测台账 / 回看校准

> discovery + observing 之上的**旁路反馈层**方案文档。定位：把系统从「只会预测、从不复盘」的**开环**，改造成「每周知道上次准不准、并据此校正」的**闭环**。
>
> 状态：**阶段 1 已落地（HYPE + sodex 双平台）**，阶段 2/3 规划中（阶段划分见 §七）。不改动现有 discovery 逻辑（observing 仅加返回值 `promotedAddresses`），只加一个侧挂数据层。sodex / HYPE 各一套 `shadow.mjs`，台账 schema 统一（阶段 2 calibrate 跨平台复用）。

---

## 一、要解决的根本问题

现在这套系统是**开环的**：每周独立预测下一批候选，却**从不回头看自己上一批预测准不准**。

- `log/discovery/` 每周记录 recommended + 全指标 = **预测记录**
- `log/observing/` 每周记录三态决策 = **持续性轨迹**

但这些全是「预测」，**没有一条「结果」**。系统从没回答过：**「上周我推荐的那批人，后来真的赚了吗？」** —— 而且这些 log 写完就烂在磁盘里，从没被回读。

**缺的不是数据量，是「给预测贴上事后结果标签，并回读它们」。**

| 现有问题 | 由哪块解决 |
| --- | --- |
| 系统只知「历史表现好」，不知「推荐之后还好不好」 | **影子跟踪**：零资金持续拉推荐地址真实盈亏，补上「事后结果」 |
| 预测与结果分离，无法配对学习 | **预测台账**：把「我说他好」和「他后来如何」配成一行，成带标签数据集 |
| 门槛/权重靠拍脑袋（`33/28/9…` 毫无事后依据） | **回看校准**：用事后数据检验哪个指标真有用，数据驱动调参 |
| 识别不了陷阱（如 PF>5 爆赚后崩盘） | **回看校准**：台账直接暴露「推荐时高分、事后崩盘」模式 |
| observing 的「连续 2 周」假设从没验证过 | **回看校准**：🟢 vs 🔴 事后表现对比，检验持续性到底有没有用 |
| 幸存者偏差：只看被推荐的，会误判「高分真有用」 | **对照组**：同时跟低分地址，才知「高分真胜过低分」而非「反正谁都赚」 |

## 二、三个组件（一条流水线）

```
影子跟踪(采结果·零资金) ──> 预测台账(预测+结果配对·可学习) ──> 回看校准(打分调参·反哺)
```

| 组件 | 是什么 | 落点 | 触发 |
| --- | --- | --- | --- |
| **影子跟踪** Shadow | 不真跟单，只持续拉「曾被推荐地址」的 positions，看它推荐**之后**真实赚没赚 | `process/shadow.mjs` = discovery ⑦ 阶段 | 每周（复用 discovery 跑） |
| **预测台账** Ledger | 一张只增不改的表，一行 = 一次预测 + 它最终的结果 | `log/ledger.json` | ⑦ 每周读写 |
| **回看校准** Calibrate | 读台账成熟行，给上一批预测打分、出调参建议 | `calibrate.mjs`（独立 CLI） | 人工 / 月度（离线，不进热路径） |

> **为什么 shadow 是 ⑦ 而 calibrate 是独立 CLI**：shadow 要跟 discovery 同频（每周记账），故进管线；calibrate 要等样本「成熟」（推荐 ≥4 周），一周变化不大，月度离线即可，不必占热路径。

## 四、澄清一个易错点：预测的不是「收入」，是「质量分」

discovery **不预测收入金额**，它预测**质量评分**（这个人值不值得跟）。校准对比的是**「分数高低」vs「实际赚多少」**，不是「预测收入 vs 实际收入」。

| | 预测侧（discovery 给的） | 结果侧（shadow 采的） |
| --- | --- | --- |
| 是什么 | 质量评分 + 指标（分 71.9 / PF 2.9 / 胜率 78%） | 实际 `realized_pnl`（推荐后真赚 $3200） |
| 不是什么 | ❌ 不是「预测他下周赚 $X」 | ✅ 是他账户真实发生的盈亏 |

**校准问的是**：我给高分的人，事后是不是真比低分的人赚得多？是 → 打分有效；否 → 打分是噪声。

## 五、数据结构：预测台账 `ledger.json`

只增不改行、逐周回填 outcome（load-modify-save，几百行规模，全量读写无压力，同 observing 模式）。

```jsonc
{
  "2026-W26|0x317a...": {
    "week": "2026-W26",
    "recommendedAt": 1782230400000,
    "address": "0x317a...", "accountId": "13462",
    "stage": "discovery",                    // discovery | observing | control（对照组）
    "predict": { "score": 71.9, "profitFactor": 2.9, "winRate": 0.78,
                 "recoveryFactor": 2.1, "netProfit": 1102, "freshNet": 340 },
    "outcome": {
      "baselinePnl": 1102,                       // 数据完整性哨兵（非计算用；某周 positions 异常时对比可发现）
      "pnlSince": { "2w": 800, "4w": 3200 },     // 推荐后各窗口新增 realized_pnl（主 2 周 + 尾 4 周）
      "tradesSince": { "2w": 5, "4w": 14 },      // 推荐后平仓笔数：区分「休眠无数据」(0笔) vs「活跃但没赚」(有笔但pnl≤0)
      "maxDrawdownSince": { "4w": -1900 },       // 推荐后期间最大回撤：识别「回本型陷阱」(浮亏扛单最后回本，跟单早爆仓)
      "lastPulledAt": 1783440000000,
      "matured": true,                           // 满 4 周冻结停跟
      "verdict": "持续盈利"                       // 校准阶段派生
    }
  }
}
```

- **平台无关**：sodex/HYPE 各自 `shadow.mjs` 算 outcome（sodex 用 `positions.realized_pnl` / HYPE 用 `userFills.closedPnl`），落台账是**统一 schema** → calibrate 可跨平台复用。
- **窗口**：主 **2 周**（快·粗，对齐 observing 节奏，快速出信号）+ 尾 **4 周**（慢·准，兜底不被 2 周噪声带偏）。冲突时以 4 周为准。

### 5.1 对照组：固定「规则」而非固定「人」

对照组存在的唯一目的是**破除幸存者偏差**——只跟推荐组会误判「选得好」还是「行情好」。从数据准确性/稳定性，形态必须是：

**规则采样对照（每周新采，非人工固定名单）**：
- **规则 = 擦边淘汰组**（刚好没过门槛的，如 PF 1.3-1.5）——落在决策边界上，信息量最高（验证「门槛线画对了吗」）
- **每周新采**：和推荐组**同周·同榜·同活跃基线** → 消除混淆变量，能干净归因到「选择质量」本身（准确性）
- **规则固定**：跨周口径一致 → 可比时间序列（稳定性）
- N = recommended 数量（正负样本平衡）
- 台账标 `stage: control`

**为什么不用人工固定名单**：人工挑 = 选择偏差（非代表性、不能泛化）+ 老化（人会休眠）+ 小 N。**把人工有偏样本并进对照组会污染统计、毁掉因果效力**——这是数据角度不可退让的红线。

**人工质疑名单（可选，另设独立流）**：若想跟「系统给高分但我怀疑」的地址，标 `stage: audit` 单独跟踪，**绝不并入 control 统计**——它回答「人机分歧谁对」的审计问题，不参与校准计算。人工的正确落点是**定规则参数**（擦边区间多宽、N 取几），不是每周挑名单。

### 5.2 影子跟踪的定位：只能证伪，不能证真

影子测「他账户赚没赚」，**永远测不到「我跟着能赚」**——滑点、跟单延迟、仓位跟不起，这三个 gap 影子看不见。所以影子跟踪是**必要非充分**：

- 影子说他**崩了** → 一定别跟（**可靠排除**）
- 影子说他**赚了** → 未必能跟（仍需执行真值/阶段 3 确认）

这个「**证伪强、证真弱**」的性质，决定阶段 1 的定位是**排除坏的**，不是**确认好的**。calibrate 逻辑与文档都须立住此点，否则会高估影子跟踪。

## 六、输出结论 & 期望结果

### 6.1 每次校准报告输出什么 = 调参建议

`calibrate.mjs` 读台账成熟行（`matured==true`），做三组分析，输出 `log/calibration/calibration-<date>.md`：

| 分析 | 问题 | 示例结论（= 调参建议） |
| --- | --- | --- |
| ① 分档命中率 | 分数有没有用？ | 高分组事后均值 +$2800 vs 对照组 −$400 → 打分整体有效 |
| ② 指标预测力 | 哪个指标真有用/是陷阱？ | PF>5 组事后崩盘率 60% → 建议 PF 封顶/降权（现权重 28 偏高） |
| ③ observing 假设 | 「连续 2 周」有效吗？ | 连续 2 周🟢 事后命中率 75% vs 单周 45% → 持续性有效，可加严到 3 周 |

**报告 = 哪个门槛/权重该改、改多少、依据是台账第几组数据。** 一期人工看了改 config（`PRESETS` 那些数字），验证校准逻辑靠谱后再谈自动调参。

### 6.2 整个体系的期望结果

让 discovery 的**评分越来越准**——「高分」从「历史看起来好」逐步逼近「跟着实际能赚」。

**质变**：系统从**每周从零重算的静态筛子**，变成**每周积累判断力、自我校正的学习系统**。终极目标——**你信任 discovery 的推荐，因为它已被几十上百条事后数据反复验证过**，而不是靠拍脑袋的权重。

## 七、落地阶段 & 边界

| 阶段 | 内容 | 前提 |
| --- | --- | --- |
| **阶段 1 ✅（HYPE + sodex 已落地）** | `shadow.mjs`（⑦）+ `ledger.json` + 对照组采样。纯采集，不校准 | 已实现：HYPE + sodex discovery ⑦ 每周随 discovery 记账。口径差异：HYPE 用 `userFills`+`aggregateTrades`（成交聚合），sodex 用 `fetchPositions`+`filter(size===0)`（逐笔已平仓位）；台账 schema 统一 |
| **阶段 2** | `calibrate.mjs` 出首份校准报告，人工调 config | 阶段 1 攒够 4 周成熟样本后 |
| **阶段 3（可选）** | 自动调参 / 执行真值接入（真实跟单的滑点/跟单率） | 阶段 2 验证校准逻辑靠谱后 |

**已锁决策**：① shadow 复用每周跑（⑦）；② 窗口主 2 周 + 尾 4 周；③ **对照组 = 规则采样（擦边淘汰，每周新采）**，人工只定规则参数，质疑名单另设 `stage:audit` 不进对照统计（见 §5.1）；④ 一期人工调参；⑤ 台账本地 JSON（同 observing 风格，gitignore VPS 本地）；⑥ shadow 纯采集，**不落 md、不推 TG**（阶段 1 无结论可报）；⑦ outcome 补 `tradesSince`（休眠歧义）+ `maxDrawdownSince`（回本陷阱）。

**边界 / 风险**：
- **旁路隔离**：⑦ 异常绝不中断 ①-⑥；calibrate 完全离线不影响生产。
- **幸存者偏差残留**：只跟被推荐的，看不到「没推荐但其实会赚的」——对照组部分缓解，非根治。
- **地址消失**：老推荐地址可能销户/无新平仓 → positions 返空，outcome 记 0/停跟，不报错。
- **不是跟单真值**：影子跟踪是「他账户自己赚没赚」，**不等于「我跟着能赚」**（滑点/跟单率差距）——那要执行闭环（阶段 3）。影子跟踪是**最便宜的近似真值**，先拿到它。

## 八、性能影响（对现有服务器）

**结论：可忽略。** 重成本（collect 流式拉整榜）完全不变，⑦ 只加少量廉价 positions 调用。

| 维度 | 增量 | 说明 |
| --- | --- | --- |
| **网络** | 每周 +~100 次 positions 调用 | 稳态跟踪数 ≈ 4 周窗 × (~10 recommended + ~10 control)/周 ≈ 80-100 地址，各 1 次；**与 evaluate 同量级，远小于 collect 的整榜流**。走现有限流（并发≤4），不飙 QPS，约给周跑加 1-3 分钟 |
| **内存** | 台账 load-modify-save | 一年 ~25 行/周 × 52 ≈ 1300 行 ≈ <1MB；全量读写零压力 |
| **磁盘** | ledger.json + calibration/ | <1MB/年 + 月度 md 报告，VPS 微不足道 |
| **CPU** | 可忽略 | JSON parse + 算术 |
| **隔离** | ⑦ try/catch，异常不中断 ①-⑥；calibrate 完全离线 | 旁路层，坏了不影响生产发现 |

**边界**：跟踪数由「4 周窗口」硬约束，不会无限增长（成熟即停跟）；台账文件只增但极小。若日后窗口拉长或跟踪量暴增，再评估转 StarRocks。

## 附录 A：阶段 2 规格级设计（calibrate，供实现无需重新分析）

> **原则**：**结构 / 算法 / 统计口径 = 现在定死**（不依赖数据）；**分档边界 / 判定阈值 / 「显著」标准 = 标 `[待阶段1数据校准]`**（依赖真实分布，现在写死等于又拍脑袋，违背 calibrate 初衷）。阶段 1 跑够 ~4 周攒出成熟样本后，照本附录实现，只需把占位阈值用真实分布填上。

### A.1 定位与触发

- **形态**：独立 CLI `service/{HYPE,sodex}-discovery/calibrate.mjs`，离线、人工/月度触发，**不进 discovery 热路径、不推 TG**。
- **输入**：读 `log/ledger.json` 的**成熟行**（`outcome.matured==true`）。
- **输出**：`log/calibration/calibration-<date>.md`（人读报告）+ 可选 `.json`（机读调参建议）。
- **CLI**：`node calibrate.mjs [--window=4w|2w] [--since=<ISO周>]`（默认全部成熟行、4 周窗口）。

### A.2 verdict 派生规则（校准时算，不存台账）

每条成熟行按 outcome 派生标签（判定线待数据）：

```
休眠      tradesSince.4w == 0                              → 剔出盈亏统计，单列「休眠率」
崩盘      pnlSince.4w < 0                                  → 负样本
横盘      pnlSince.4w ≈ 0 且 tradesSince.4w > 0            → 活跃但没赚（弱负）
回本陷阱  pnlSince.4w > 0 但 |maxDrawdownSince.4w| 过深     → 账面赚但跟单会爆仓（危险！算负）
持续盈利  pnlSince.4w > 0 且 回撤可控                       → 正样本
```

> 「≈0」带宽、「过深」回撤线 = `[待阶段1数据校准]`（看真实分布定分位）。**回本陷阱**是关键——账面正收益但中途巨亏，跟单的人早爆仓离场，必须算负，否则高估。

### A.3 三组分析（算法框架固定，阈值待定）

**① 分数有效性（推荐组 vs 对照组）**
```
分组：stage=discovery  vs  stage=control（过门槛未入选 topK）
各组算：pnlSince.4w 的 { 正收益占比, 均值, 中位数, 回本陷阱率, 崩盘率 }
结论：discovery 显著优于 control → 打分/topK线有区分度；无差 → 打分线随意需重审
显著性：小样本用「中位数对比 + 符号检验 + 趋势」，报告标「小样本·趋势非定论」
```

**② 指标预测力（逐维分档，抓陷阱）**
```
对每个 predict 指标（HYPE: profitFactor/winRate/recoveryFactor/tradesPerDay；sodex 同口径）：
  按值分档（如 PF: <2 / 2-3 / 3-5 / >5）  ← 分档边界[待数据校准]
  各档算 pnlSince.4w 均值 + 回本陷阱率 + 崩盘率
输出：哪个档「推荐时高分、事后崩」→ 该指标该封顶/降权
典型待验证假设：PF>5 组崩盘率高（爆赚回归）→ 建议 PF 封顶
```

**③ observing 假设检验（持续性有没有用）**
```
分组：stage=observing（连续2周🟢） vs stage=discovery（单周未promoted）
比 pnlSince.4w 均值/正占比/回本陷阱率
→ observing 显著更好：连续2周有效，可加严到3周；无差：持续性无增量回炉
（🔴 移出地址事后表现从 observing log 关联，作反向验证）
```

### A.4 报告结构（`calibration-<date>.md`）

```
# 校准报告 <date>（窗口 4w）
## 样本概览  成熟N条（discovery A / observing B / control C）· 休眠率X% · 回本陷阱率Y%
## ① 分数有效性  discovery 中位 vs control 中位 → 结论
## ② 指标预测力  逐维分档表（均值/崩盘率/陷阱率）→ 陷阱指标标红
## ③ observing假设  🟢组 vs discovery组 → 持续性结论
## 调参建议  [改哪个门槛/权重][改多少][依据第几组][置信度：小样本/趋势/可信]
```

### A.5 阶段 2 落地清单

- 新建 `calibrate.mjs`（独立 CLI）+ `log/calibration/` 目录
- 复用台账 `ledger.json`（阶段 1 产物）；sodex/HYPE 台账统一 schema → calibrate 跨平台复用
- **一期人工**：报告只出建议，人看了改 `config` 的 `PRESETS`；靠谱后（阶段 3）再谈自动调参

### A.6 与阶段 1 的接口契约（关键，防漂移）

阶段 2 只依赖阶段 1 台账的这些字段（阶段 1 spec 须保证产出）：

| calibrate 需要 | 阶段 1 台账字段 | 用途 |
| --- | --- | --- |
