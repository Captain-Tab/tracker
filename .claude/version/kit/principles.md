# Principles 变更日志

> 版本约定：SemVer，第一个 `## v<x.y.z>` 即当前版本。
>
> 本模块存放 sosokit spec-kit 的核心设计原则，policy / enforcement 分离架构中的 **policy 中心**。

## v1.2.0 - 2026-05-09

### 🎯 新增模块：evidence-grounding.md（证据落地）

**背景**：sodex-next AppKit Connect Modal 复盘暴露的 LLM 评估失效——AI 第一轮把 modal=false 评级"中-高风险"，理由是"听起来要改基础设施"，用户追问后完整 Read 源码才发现基础设施已实现，评级降为"低"。这不是个案，是 LLM 用语言相似性匹配代替源码事实的固有特性。

**核心命题**

> 判断坑不坑，靠的是能否把每条风险落到具体源码行——落不到行的风险都是脑补。

**三类证据形式**

| 形式 | 例子 | 强度 |
|---|---|---|
| A. 源码行号 | `path/to/file.ts:42-50 实现` | ⭐⭐⭐⭐⭐ |
| B. 测试/文档段落 | `types.ts:45 公共 API` | ⭐⭐⭐⭐ |
| C. 显式推理 | `[推理] 依据：A 形式的 X.ts:N` | ⭐⭐ |
| D. 无引用 | "听起来"/"通常"/"可能" | ❌ 禁止 |

### 🔄 新增第 5 条第一性原理：证据落地

**改动**：两个家族 `rules/modules/<family>/constitution.md` 同步追加第 5 条：

```
5. 证据落地 — 风险/复杂度/可行性评级必须能指向源码行号；
   找不到行号的判断标 [推理] 或回去补读。
   "听起来"/"通常"/"可能"是反模式。
```

定位：与第一性原理 ②（路径最短）、③（追根因）形成"思考品质三角"——思考起点对、判断品质实、严格度合理。

### 🔧 命令补丁：commands/k/plan.md

在 L283 区域 `### 4. 风险与计划自审 → A. 技术风险点` 加证据要求：

- 每条风险点必须配 `file:line` 范围证据，或标 `[推理]` + 推理来源
- 给出正/反例对照

**为什么只改 plan.md**：

| 命令 | 现状 | 是否改动 |
|---|---|---|
| `/k:plan` | 风险自审存在但未要求证据列 | ✅ 加 1-2 行 |
| `/k:debug-on` | 已用 `Code Path: file:line` 格式 | ❌ 不动 |
| `/k:check` | CHK-04c 已做 absence-of-evidence | ❌ 不动 |
| `/k:clarify` | constitution.md 兜底 | ❌ 不动 |

**判断依据**：基于源码核查（`grep -n "evidence|证据|file:" commands/k/plan.md commands/k/debug-on.md`）。这本身就是证据落地原则在自己设计上的应用。

### 反思：为什么 v1.1.0 没包含这一条

复盘中识别的设计盲点：

1. **机械外推**：把"4 条第一性原理 → 4 个对应命令"的处理模式套到证据落地，没意识到它是横切关注点
2. **没读源码下结论**：之前判断"命令本身是原则的实现"时未实际读 plan.md / debug-on.md，被用户追问后才纠正
3. **辩护惯性**：被质疑"为什么不动 plan/debug"时第一反应是辩护已有判断，而非回去补读源码——讽刺地违反了刚立的"证据落地"原则

### 适用场景

| 场景 | 触发 |
|---|---|
| 多方案对比的成本/风险评级 | ✅ 强触发 |
| Bug 假设的可能性排序 | ✅ 触发 |
| 复杂度估算 | ✅ 触发 |
| 改文案 / 调样式 / 概念解释 | ❌ 不触发 |

### 已知局限

- LLM 可能学会"列假证据"——糊弄式合规规则本身无法识别，需用户抽查
- 第 5 条与第 ③ 条"日常开发不过度根因化"在边界场景可能轻微冲突
- 实战观察 2-3 次后再决定是否升级到 Level 3（对抗性自审）

### 三层职责清晰度验证

本次新增**没有**违反 v1.1.0 立的三层职责硬规则：

| 层 | 改动 | 是否越界 |
|---|---|---|
| 思想层 | 新增 `evidence-grounding.md` | ✅ 写"为什么" |
| 生效层 | constitution.md 加 1 行 | ✅ 仅声明，不展开 |
| 执行层 | plan.md 加格式约束（不嵌入原则全文） | ✅ 仅做命令本职已有结构的微调 |

## v1.1.0 - 2026-05-09

### 🎯 新增模块：first-principles.md（第一性原理）

**背景**：基于 2026-04-22 Claude Code 洞察报告的 56 个会话复盘——5 类高频摩擦（方向错误 30 / 误解需求 25 / 改动范围过大 11 / 代码 Bug 15 / 用户冗余汇报）反复出现，需要前置元原则消灭它们。

**核心命题**

> 从需求本质出发，不从惯例或模板出发；说该说的，做该做的；其余皆是噪音。

**四原则模型（每条带场景限定，避免日常小任务被过度审慎）**

| 原则 | 对治反模式 | 关键场景 |
|---|---|---|
| ① 动机优先 | 假设用户已想清楚 → 闷头开干 → 做错方向 | 方向性决策或不可逆操作时停下；明确小任务直接执行 |
| ② 路径最短 | 给"看起来完整"的方案 → 用户接受才发现绕路 | 主动告知更短路径，宁可在 plan 阶段被否 |
| ③ 追根因 | 看到症状就修 → 同类问题反复出现 | bug / 异常 / 反复问题必须追根因；日常开发不过度根因化 |
| ④ 信息精简 | 把过程当成果交付 → 真正决策点被掩盖 | 砍掉不改变决策的信息；不复述代码已表达的事实 |

### 🔧 新增模块：README.md（思想层索引 + 三层职责架构）

**三层职责硬规则**（防止未来扩展时职责越界）：

| 层 | 位置 | 职责 | 不要做 |
|---|---|---|---|
| 思想层 | `kit/principles/` | 写"为什么"、反模式分析、决策表 | ❌ 写"如何执行"步骤 |
| 生效层 | `rules/modules/<family>/constitution.md` | 声明优先级 + 引用本目录 | ❌ 展开思想内容 |
| 执行层 | `commands/k/*.md` | 命令本身是原则的具体化 | ❌ 嵌入原则全文重复 |

**扩展机制**：未来加新元原则只需 3 步——新建文件、更新 README 表格、constitution 加链接。constitution 永远 ≤ 30 行（不含项目特定原则），靠引用而非展开。

### 🔄 重写：rules/modules/<family>/constitution.md（生效层落地）

**改动**：从空占位文件改为元原则可执行摘要。sodex-web / sodex-next 两个家族同步更新。

**关键设计决策**：

| 维度 | 旧版本 | 新版本 |
|---|---|---|
| 内容 | 空占位（仅注释模板） | 4 条第一性原理 + 3 层严格度模型 |
| AI 视角 | 看不到任何元原则 | 全部可执行指令直接展开 |
| 文档链接 | 无 | 末尾列出 principles/ 路径 |
| 字数 | 17 行 | 37 行 |

**避免"详见 X.md"陷阱**：AI 不会自动跟进文档链接，所有可执行内容必须在 constitution.md 内自包含。principles/ 文档仅供人工查阅，扩展规则时参考。

### 反思：为什么没在 v1.0.0 就这样设计

复盘中发现的设计陷阱：

1. **类比偏差**——用人类工程师"模块化引用"心智模型套到 AI 输入设计上
2. **没做 AI 视角验证**——未问"如果我是 Claude，只看到这文件能拿到所有指令吗"
3. **被"分层完整"诱惑**——好设计标准是最小完成目标，不是分层完整
4. **未把已有原则用到自己身上**——第一性原理 ② 路径最短，在自己的设计上没遵守

**沉淀的元教训**：设计 AI 输入时，每写一条"详见 X"都要问——X 会被 AI 读到吗？会 → 直接展开；不会 → 标注定位（人工查阅）。

### 适用场景

`/k:clarify` `/k:plan` `/k:debug-on` 等所有命令的元原则兜底；`/k:` 之外的日常会话保底覆盖。

### 已知局限

- 4 条原则尚未在多次真实需求中验证摩擦消灭率
- "动机不清就停下"与 Auto mode 的协同尚未观察
- README 三层职责能否在未来扩展中维持清晰，需 2-3 次新原则加入后定论

## v1.0.0 - 2026-05-06

### 🎯 模块创建：strict-vs-cumbersome.md

**背景**：`wcRelayRestart` 迁移需求复盘归纳出关键设计原则——「严格」≠「繁琐」。文档化后作为 sosokit 后续 enforcement 改造的判断框架。

**核心命题**

> AI 工程不应模仿传统软件工程的"流程繁琐"——AI 的工序成本 ≠ 人的注意力成本。把严格塞进 AI 内部工序，把简洁留给用户审查——这样 spec-kit 既能拦下错误，又不会让用户嫌烦。

**三层模型**

| 层 | 谁承担成本 | 严格收益 | 设计原则 |
|---|---|---|---|
| 输出层（用户看到的报告 / 标注 / 对照表） | 用户审查成本 ↑↑ | 中 | 谨慎——越长越难审 |
| 工序层（AI 内部 grep / Read / 自检） | token 成本（用户不直接感知） | 高 | **追求严格** |
| 规则层（CLAUDE.md / always-on header） | 上下文占用 + 易被 skim | 中（取决于条数） | 少而精，≤5 条核心 |

**适用场景**

`/k:clarify` `/k:spec` `/k:plan` `/k:task` `/k:check` 各阶段的工序设计、自检模板、enforcement 落点判断。

**反向引用入口**（同步落地的 enforcement，见 `commands/k.md` v2026-05-06）

```
.claude/kit/clarify/scripts/spec-lint.sh        → §4.1（工序失败时才生成输出）
.claude/kit/check/templates/checklist.md:CHK-04c → §3 决策表
.claude/commands/k/clarify.md Step 6.0          → §4.3 正 pattern
.claude/commands/k/plan.md Step 4-C             → §3 信息缺口
.claude/commands/k/plan.md 确认流转             → §3 同意 ≠ 免责
```

**与 `.claude/rules/` 的关系**

- `.claude/rules/` 已 14 个文件——本模块**不**新增 always-on 规则（避免被 skim）
- 元认知约束（absence-of-evidence / 信息缺口 / 反 agreeable）做成**工序级 enforcement** 嵌入命令，不放规则层

**已知局限**

- 原则未在多次真实需求中验证（仅基于 1 次复盘）
- enforcement 触发率需观察 2-3 次真实需求才能定论
- 「严格 vs 繁琐」的判断仍含主观成分（"用户审查成本"无客观度量）
