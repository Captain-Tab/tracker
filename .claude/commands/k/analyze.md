# Analyze: 既有项目模块逆向分析

## 用户输入

```text
$ARGUMENTS
```

---

## 核心定位

将既有项目的某个或某些模块逆向分析为**纯事实参考文档**，供后续方案设计 / 评估使用。

**与相邻命令的边界**：

| 命令 | 输入 | 产出 | 适用场景 |
|---|---|---|---|
| `/k:clarify` | 模糊想法 | 设计 spec（含验收场景） | 要做的功能尚未明确 |
| `/k:spec` | 已确认设计 | 功能实现规范 | 准备进入实现 |
| `/k:study` | GitHub 项目 + soso-kit 对比 | 借鉴裁决报告 | 评估外部项目对工具链的启发 |
| **`/k:analyze`** | **既有项目模块 + 范围** | **带源码定位的纯事实分析文档** | **理解现有代码（迁移参考 / 重构依据 / 知识沉淀）** |

<HARD-GATES>
1. **纯分析、零代码改动**：本流程不修改任何源代码文件
2. **强制源码定位**：所有产出表格的每一行必须含 `file:line` 列。无定位 = 模糊点
3. **无主观建议**：不写"迁移建议"、"风险评估"、"优化方向"、目标技术栈专属概念（如 sodex-next 的 Stream/Command Service）。只描述事实
4. **模糊点终止机制**：仅当源码无法定位时暂停询问用户；产品/逻辑解读问题不阻塞，写进文档继续推进
5. **行为完整性追溯**：分析任何接口 / 函数时，必须追到上游 caller / 下游 callee / 路径上的横切层（middleware / interceptor / hook / decorator / event listener）。未追溯 = 模糊点，归入文档末尾「上下游缺失」段

   > **动机**：跨项目对比时陷入"接口层伪等价"——只看相同函数实现就抄，没把上下游隐式行为算进去。例：A 项目 service 不做校验是因为 caller 做了 → 抄 service 又没看 caller → 漏校验。"实现行为 = 接口层 + 上下游层 + 横切层 的总和"

6. **文档头部消费提示（强制）**：产出 `<topic-slug>-analysis.md` 时，文档最开头**必须**包含以下消费提示块（紧跟文档标题之后）：

   ```markdown
   > ⚠️ **消费提示**：本文档作为跨项目对照 / 迁移参考 / 重构依据使用时，
   > **必须读章节 7「行为流追溯」+ 文末「上下游缺失」段**——
   > 仅看接口层（章节 2 / 3）会陷入"接口层伪等价"陷阱：
   > 看到两个项目的 service 函数实现相似就直接抄，但行为分布在上下游层
   > （caller 校验 / middleware 鉴权 / hook 副作用）的差异会被漏看。
   >
   > **实现行为 = 接口层 + 上下游层 + 横切层 的总和**。
   ```

   > **动机**：HARD-GATE 5 让 analyze 产出端含上下游层信息，本规则让消费端不会跳过章节 7。无消费提示头部 = 文档不完整。
</HARD-GATES>

## 执行步骤

### Step 0：解析输入

**输入优先级**（按顺序匹配）：

1. `$ARGUMENTS` 指向 `.claude/kit/spec/` 下某个 `.md` 文件 → Read 文件作为分析任务说明
2. `$ARGUMENTS` 是其他绝对路径 / 相对路径的 `.md` 文件 → Read 文件
3. `$ARGUMENTS` 是文字描述（含项目路径 + 模块名）→ 直接作为任务说明
4. 以上都不命中 → **报错并反问用户**，禁止猜测：

```
❌ 未找到分析任务说明。请提供以下任一形式：
  - 任务说明文档路径（建议放在 .claude/kit/spec/ 下）
  - 任务文字描述（说明：要分析的项目根路径 + 模块名 / 入口文件 + 关注范围）

例：/k:analyze .claude/kit/spec/sosovalue-trade-news-overview.md
例：/k:analyze 分析 /Users/xxx/projectA 的支付模块 src/payment/，关注接口和处理逻辑
```

输出：
- 命中文件 → `📄 已读取任务说明：<文件名>`
- 文字输入 → `💬 从对话输入理解任务`

---

### Step 1：澄清范围（最多 5 问）

**只在以下信息缺失时提问**，齐全则跳过：

| # | 问题 | 何时问 |
|---|---|---|
| Q1 | 要分析的项目根路径？ | 输入未明确给出绝对路径 |
| Q2 | 模块定位（入口文件 / 目录 / 路由）？ | 输入未指明模块 |
| Q3 | 关注范围（接口 / 处理逻辑 / 类型 / 实时性 / 分支差异 / 其他）？ | 输入未限定关注面 |
| Q4 | 最终用途（迁移参考 / 重构依据 / 知识沉淀）？ | 影响产出聚焦点（仅作记录，不影响"无主观建议"红线） |
| Q5 | 是否有对照对象（成对分析的另一侧项目/模块）？若有，它将 join 在什么键上（如"对方下游靠 wagmi useAccount"）？ | 仅当用途=迁移参考且存在对照侧。**只用于提示本次多收 join 键事实，不做对照结论** |

> **成对模式约束（红线）**：Q5 有答时，本次需把"对照侧将依赖的承重事实"（如下游 join 在哪个 hook/接口/字段上）显式收入文档并标注。但**仅收事实、禁下对照结论 / 优劣判断 / 迁移建议**——否则退化为 `/k:study`，违反 HARD-GATE 3。

**截图驱动的范围纠偏**：

> 若用户在对话中提供截图（UI 标注 / 模块矩阵），**以截图为准**覆盖文字理解。文字描述与截图冲突时主动反问，禁止默默按文字执行。

---

### Step 2：复杂度判定（决定执行路径）

读取入口文件 + 列出模块根目录，按以下维度评估：

| 维度 | 简单 | 复杂 |
|---|---|---|
| 子模块数 | ≤ 3 | > 3 |
| 关注维度数（B/C/D/E/F 中涉及几个） | ≤ 2 | ≥ 3 |
| 跨文件耦合 | 集中在 ≤ 5 个文件 | 跨 6+ 文件 / 跨 hooks/store/utils |
| 资产类型 / 业务分支 | 无分支或单一分支 | 多分支（如 CEX/DEX、多资产类型） |

> 任一维度命中"复杂"列 → 走 **复杂模式（多 agent 并行 + 分段验证）**；全部命中"简单"列 → 走 **简单模式（单 agent 一次完成 + 一次验证）**

输出：

```
🔍 复杂度判定：<简单|复杂>
   依据：<维度1=值; 维度2=值; ...>
   执行路径：<简单模式 | 复杂模式>
```

---

### Step 2.5：依赖接线扫描（条件触发）

**触发条件**（命中任一才执行，否则跳过——避免对纯业务模块产生噪音）：模块文件 import 了第三方 SDK / 钱包 / 鉴权 / 支付等外部集成库，或 Step 1 用途为「迁移参考」。

执行（纯事实收集，**由主 agent 直接做**——读 package.json + grep 成本低，无需派子 agent）：

1. 读 `package.json`，列出与本模块相关的依赖 + 版本号
2. 对每个相关依赖 `grep` 全仓引用，判定**接线状态**：已接线（在哪 file:line）/ 已安装未使用 / 仅类型引用
3. 收录为事实表格：`依赖 | 版本 | 接线状态 | file:line`

**落地**：主 agent 在最终文档生成后，把本表作为**章节 8**追加写入 `<topic-slug>-analysis.md`（简单模式：在单 agent 产出文档后由主 agent append；复杂模式：在 Step 4 汇总时并入）。不占用 Step 3 的分析 agent。

> **边界（硬约束）**：只收录"装没装 / 在哪接线 / 是否使用"这类**可源码定位的事实**。**禁止**写该 SDK "怎么用 / 能力如何 / 是否适合迁移"——那是外部文档 / `/k:study` / 方案设计的职责，写入即违反 HARD-GATE 3。

> **动机**：迁移/集成类分析里，"某桥接库已装但未接线""某 connector 在 X 处创建"是承重事实，但只扫 `src` 行为会漏掉 `package.json` 维度。

### Step 3-A：简单模式

单 agent 直接产出最终文档：

```
派 Explore agent，任务：
- 项目根：<PROJECT_PATH>
- 模块：<MODULES>
- 范围：<SCOPE>
- 产出：单文件 .claude/kit/spec/<topic-slug>-analysis.md
- 文档结构（从 7 章中选用户关注的章节，未命中的章节直接省略；章节 7 强制产出，不可省）：
  1. 模块矩阵
  2. 接口清单（表格列：路径 / 方法 / 参数 / 返回字段 / SSR-CSR / 调用位置 / 接口定义位置）
  3. 处理逻辑（表格列：函数 / 函数位置 / 调用位置 / 输入 / 输出 / 说明）
  4. 分支差异（表格列：判断条件 / 判断位置 / 各分支走向）
  5. 实时性 / 通信(表格列：通道 / 推送字段 / 订阅入口 / 取消订阅 / 重连)
  6. 类型定义（表格列：类型名 / 位置 / 用于模块 / 关键字段）
  7. **行为流追溯**（强制章节，按 HARD-GATE 5；表格列：核心函数 file:line / 上游 caller file:line + 前置处理 / 下游 callee file:line + 后置处理 / 横切层 file:line + 作用）。追溯不到的函数 / caller / callee / 横切层 → 归入文档末尾「上下游缺失」段，不阻塞
  （章节 8「依赖与接线状态」不在本 agent 职责内——若 Step 2.5 触发，由主 agent 事后追加）
- 红线：
  - 每行表格必填 file:line（无定位 = 列入文末"模糊点"）
  - 不写迁移建议 / 风险评估 / 目标技术栈专属概念
  - 仅在源码无法定位时停下询问；产品/逻辑解读问题写进模糊点继续推进
```

跳到 Step 5（验证）。

### Step 3-B：复杂模式（多 agent 编排）

#### 3-B.1 任务拆分

按以下 6 类拆分，**根据 Step 1 的关注范围**选取需要的任务（未命中的任务跳过）：

| 任务 | 内容 | 并行性 |
|---|---|---|
| A | 模块定位（路由 / 入口 / 子模块矩阵） | **串行前置**（即 Step 1+Step 2 已产出） |
| B | 接口清单 | **可与 C/F 并行** |
| C | 处理逻辑 | **可与 B/F 并行** |
| F | 类型定义 | **可与 B/C 并行** |
| D | 分支 / 差异 | **依赖 B + C** |
| E | 实时性 / 通信 | **依赖 B** |
| **G** | **行为流追溯**（按 HARD-GATE 5：caller / callee / 横切层） | **依赖 B + C**，可与 D / E 并行 |

#### 3-B.2 并行派单（B / C / F）

同时派 3 个 Explore agent（独立产出 task 文档）：

```
- task-B.md（接口）
- task-C.md（逻辑）
- task-F.md（类型）
路径：.claude/kit/spec/<topic-slug>-task-{B|C|F}.md

每个 agent 红线：
- 每行表格必填 file:line
- 范围严格限定为 Step 1 的模块边界
- 模糊点写到文档末尾，不阻塞
```

> **冲突检测**：B/C/F 完成后，主 agent 必须 cross-check 三者结论。例如 F 说有 N 个分立类型，但 B/C 没看到对应分支 → 在 D 的派单 prompt 里**显式标出冲突点要求澄清**，避免分支结论失真。

#### 3-B.3 串行派单（D / E）

B/C/F 完成后，并行派 D / E / G（按需）：

```
- task-D.md（分支）：必读 task-B/C/F.md
- task-E.md（实时性）：必读 task-B.md
- task-G.md（行为流追溯）：必读 task-B/C.md
  红线：
  - 对每个核心函数追：上游 caller / 下游 callee / 横切层（middleware / interceptor / hook / decorator / event listener）
  - 每行表格必填 file:line
  - 追溯不到 → 归入文末「上下游缺失」段，不阻塞
  - 禁止把"未发现 = 不存在"当结论，必须明确写"已 grep <模式>，未命中"
```

#### 3-B.4 自动推进 vs 模糊点暂停

- **不**要求用户逐任务确认，B → D → E 自动推进
- 仅当某任务产出大量 `file:line` 缺失的模糊点，且无法通过追加 grep 定位时，才停下询问用户

### Step 4：汇总文档（仅复杂模式）

将 task-{B|C|D|E|F|G}.md 合并到最终文档：

```
.claude/kit/spec/<topic-slug>-analysis.md
```

文档结构（**纯事实合并，无主观章节**）：

```
1. 分析范围与模块矩阵
2. 接口清单（合并 Task B）
3. 处理逻辑（合并 Task C）
4. 分支 / 差异（合并 Task D）
5. 实时性 / 通信（合并 Task E）
6. 类型定义位置（合并 Task F）
7. 行为流追溯（合并 Task G）  ← 强制章节，按 HARD-GATE 5
8. 依赖与接线状态（合并 Step 2.5，仅触发时）  ← 只收事实，禁写 SDK 用法
末尾：上下游缺失（task-G 未追到的项，归入此段）
```

章节 2-6 未涉及的可省；**章节 7 不可省**（HARD-GATE 5 要求）；章节 8 仅 Step 2.5 触发时产出。

---

### Step 5：核验（强制，对抗式）

派一个**核验 Explore agent**，指令为**证伪导向**——默认假定文档有错，目标是"挑出错的"而非"确认对的"。

**抽样量按复杂度浮动**（不固定）：简单模式 ≥10 条；复杂模式 ≥18 条，且**对最复杂/最长的子文档（通常行为流 task-G）加大抽样权重**（该文档至少占总抽样的 40%）。

| 维度 | 检查内容（证伪措辞） |
|---|---|
| **真实性** | 抽样 `file:line`，逐条 Read 源码**找出与描述不符之处**。分类 ✅ 准确 / ⚠️ 偏差 / ❌ 错误（含行号错位、范围过宽、结论与源码相反） |
| **完整性** | 章节间是否存在**矛盾**（接口与处理逻辑、分支与矩阵、类型与 DTO 冲突） |
| **遗漏** | 范围内被忽略的子模块 / 端点 / 处理函数 / 类型；**反向 grep 触点清单核对是否齐全** |
| **模糊度** | 读者无法据此确定行为之处 |
| **行为流完整性** | 抽样 5~8 个核心函数，反向 grep 验证上下游 + 横切；漏追的列入「上下游缺失」 |

核验 agent 仅输出报告（不写文件、不改源码），格式：

```
真实性：N 准确 / N 偏差 / N 错误（逐条：引用 → 实际 → 判定）
完整性：N 处缺失 / N 处矛盾
遗漏：列具体项 + file:line
模糊度：列具体项
```

主 agent 收到核验结果后：

- **修正前必须二次核实**：对抗式核验可能过报，主 agent 对每条 ❌/⚠️ 先自行 Read 源码确认属实，再改；**禁止照单全收**（防过度证伪引入新错）。
- 真实性 < 90% 或出现已核实的 ❌ → 修正最终文档对应条目
- 完整性 / 遗漏 → 视严重性补齐（关键缺失必补；细节遗漏归到模糊点）
- 模糊度 → 视情况补 grep 后修正，或保留为模糊点

修正完毕，输出修订摘要（含"核验报告 N 条、二次核实属实 M 条、已修 M 条"）。

### Step 6：交付

```
✅ 分析完成

📄 主文档：.claude/kit/spec/<topic-slug>-analysis.md
📋 章节覆盖：<列出已生成的章节序号>
🔍 核验结果：真实性 N% / 完整性 OK / 遗漏 N 项 / 模糊度 N 项
🔗 行为流：覆盖 N 个核心函数 / 上下游缺失 N 处（详见文末「上下游缺失」段）
⚠️ 待澄清模糊点：<前 3 条>（完整列表在文档末尾）

下一步：
- 直接用于方案设计/评估
- 若发现重大遗漏 → 重新运行 /k:analyze 补充
- 若进入实现 → /k:spec 加载本文档
```

## 适用 / 不适用

✅ **适用**：
- 逆向分析既有项目的某个或某些模块
- 为迁移 / 重构 / 知识沉淀准备参考文档
- 跨项目对比某一类实现（拆成两次分析 + 手动对照）

❌ **不适用**：
- 要做的功能尚未明确 → 用 `/k:clarify`
- 已经有设计要进入实现 → 用 `/k:spec`
- 评估外部 GitHub 项目对工具链的启发 → 用 `/k:study`
- 修复 bug / 调试 → 用 `/k:debug-on`
