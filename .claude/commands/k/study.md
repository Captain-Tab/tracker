# Study: 项目研究分析

## 用户输入

```text
$ARGUMENTS
```

---

## Phase 1: 解析项目

执行项目解析脚本：

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/study/scripts/resolve-project.sh" "$ARGUMENTS"
```

**根据 JSON 输出处理：**

- `status: "error"` 或 `status: "not_found"` → 输出 message 内容，**终止流程**
- `status: "found"` → 记录 LOCAL_PATH、REPO、PROJECT_NAME，继续
- `status: "cloned"` → 记录同上，提示 `📦 已 clone 到本地`，继续

---

## Phase 2: 更新项目代码

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/study/scripts/update-project.sh" --path "<LOCAL_PATH>"
```

记录 COMMIT、BRANCH、UPDATED 状态。若 `updated: false`，输出 message 中的警告但继续流程。

---

## Phase 3: 检查 soso-kit 自画像

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
PROFILE="$KIT_ROOT/.claude/version/soso-kit-profile.md"
if [ -s "$PROFILE" ]; then
    echo "EXISTS"
    stat -f "%Sm" -t "%Y-%m-%d" "$PROFILE"
else
    echo "EMPTY"
fi
```

**处理逻辑：**

- `EMPTY`（文件不存在或为空）→ 自动执行 generate-profile.sh 生成自画像
- `EXISTS` → 询问用户：

```
📄 soso-kit 自画像已存在（上次更新：<日期>）
是否需要更新？(Y/n)
```

- 用户选 Y → 执行 generate-profile.sh：
  ```bash
  bash "$KIT_ROOT/.claude/kit/study/scripts/generate-profile.sh"
  ```
- 用户选 n 或跳过 → 使用现有自画像

---

## Phase 4: 扫描目标项目

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/study/scripts/scan-project.sh" --path "<LOCAL_PATH>" --name "<PROJECT_NAME>"
```

记录扫描输出为 SCAN_RESULT，注意末尾的 token 估算值（SCAN_TOKENS）。

---

## Phase 5: 加载自画像

使用 Read 工具读取：

```
$KIT_ROOT/.claude/version/soso-kit-profile.md
```

---

## Phase 6: 深入分析（目标项目侧）

基于 Phase 4 扫描结果和 Phase 5 自画像，执行深入分析：

1. **识别关键文件**：从扫描结果中找出核心源码文件（入口文件、配置文件、核心模块、命令/工作流定义）
2. **深入阅读**：使用 Read 工具读取关键文件（控制在 5-10 个文件内，避免 token 爆炸），每个判断都记下来源 `file:line`
3. **逐单元深挖实现细节**：对目标项目的**每个命令 / 核心模块 / 关键流程**，拆解它的实现细节——内部用了什么控制流、数据结构、交互范式、校验/闸门、token 策略，以及"为解决什么问题"。这是 Phase 6.45 亮点机制提炼的素材，必须落到 `file:line`。
4. **草拟候选借鉴点**：列出目标项目可能值得 soso-kit 借鉴的点——**仅列清单，此时禁止定级 ✓/✗/~**。定级一律留到 Phase 6.5 验证后

**分析维度（必须全部覆盖）：**

| 维度 | 要求 |
|------|------|
| 核心思想与原则 | 项目的设计理念、指导原则 |
| 核心流程 | 主要工作流、架构概览；**必出 ASCII 流程图**（见 Phase 6.6 HARD-GATE） |
| 优势与劣势 | 客观评估 |
| 亮点机制提炼 | 逐命令/模块拆出值得学习的标志性机制，**独立于借鉴裁决**；详见 Phase 6.45 |
| 与 soso-kit 对比 | 基于自画像做表格对比 |
| 借鉴建议 | 经 Phase 6.5 验证后再定级；质量四问见 Phase 6.4，裁决与五问见 Phase 6.6 |

> ⚠️ 自画像（Phase 5）是 soso-kit 的**抽象摘要**，只用于「目标项目像/不像 soso-kit」的方向判断。**禁止**拿它当「soso-kit 是否已有 / 是否需要」的依据——那必须落到 soso-kit 源码（Phase 6.5）。自画像没提 ≠ soso-kit 没有。

## Phase 6.4: 分析质量四问（强制元自检，先于裁决）

第一性原理：**错误的「零借鉴」比错误的借鉴更隐蔽**——它伪装成「严谨拒绝」，实则是没读够 / 没取证 / 懒得挖。进入 Phase 6.5 逐候选裁决前，先对「分析本身」做四问体检。这是对**分析**的体检，Phase 6.5 是对**每个候选**的裁决，两者都要做，不可互相替代。**任一问不过 → 回 Phase 6 补读，禁止带病进入裁决。**

| # | 自检问 | 通过条件 | 不通过则 |
|---|--------|---------|---------|
| 1 | **信息是否充分？** | 已读到目标项目的**核心闭环**（不止 README / schema / 架构外壳），能指出它「完整跑一遍」的关键机制 `file:line`（如归档合并、状态流转、注入组装、解析主体） | 只读了外壳 → 回 Phase 6 补读核心流程源码 |
| 2 | **依据是否实际代码？** | 每条「已有 / 缺失」判断都指向 **soso-kit 源码 `file:line` 或实测命令输出** | 任何一条引自**自画像 / 记忆 / 「通常」「可能」** → 作废该判断，回源码取证（呼应 Phase 6 自画像禁令） |
| 3 | **确定没有可借鉴吗？（反武断全否）** | 若倾向「全否」，须逐候选证明：每个都有 soso-kit 源码反证，且已下钻到目标项目**最精细的差异层**（注入策略 / 校验闸门 / 上下文裁剪等实现细节） | 凭「理念高度同构」一笔带过就收手 → 武断，回 Phase 6 挖细节差异 |
| 4 | **深度是否到位？** | 已对比到「同一目的、不同实现」的**实现差异**，能说清差异的真实代价（token / 正确性 / 可维护性） | 停在功能名 / 理念对比 → 继续下钻到机制实现 |

**硬约束：**

- 「无可借鉴」是合法结论，但必须是**穷尽细节后**的结论，不是**懒得挖**的结论。第 3 问专防后者。
- 四问任一不过禁止进入 Phase 6.5；通过后在裁决摘要附近用一句话标注「分析质量四问已过」。

## Phase 6.45: 亮点机制提炼（强制，独立于借鉴裁决）

第一性原理：**「是否适合 soso-kit」与「是否值得学习」是两个正交问题。** Phase 6.5 只回答前者（零假设 = 不借鉴）；本阶段只回答后者，**不走零假设、不做反向验证、不要求 soso-kit 缺失证据、不定 ✓/✗/~**。一个机制完全可能「不适合搬进 soso-kit，但其设计思想极值得学习」——这类洞察是 study 的核心产出之一，绝不能被借鉴裁决吞掉。

**定义「亮点机制」**：目标项目里**为解决某类普遍难题而设计的、有辨识度的标志性机制**。判定它够格的三个特征（满足任一即可入选）：

- **把主观/隐性的东西显式化**：将"凭感觉判断"转成可量化、可复现、可分级的结构（如把质量/可信度/复杂度转成评分或档位、把口头约定固化为显式闸门）。
- **思想内核可迁移**：脱离该项目语境后，这套做法仍能套用到任意同类工具上。
- **实现方式非显然**：不是行业默认写法，存在"原本可以更糙但它选择更巧"的设计取舍。

**逐单元提炼（基于 Phase 6 step 3 的深挖素材）：**

对每个入选机制，输出四要素，每条**必须附目标项目源码 `file:line`**（提炼的是实测代码，不是想象；找不到行号 → 删除该条，禁止编造）：

| 要素 | 要求 |
|------|------|
| ① 机制名 | 一个有辨识度的短名（动宾或名词短语） |
| ② 解决什么问题 | 它针对的那类普遍难题（一句话） |
| ③ 怎么实现的 | 实现细节：控制流 / 数据结构 / 交互范式 / 闸门 / token 策略，附 `file:line` |
| ④ 可迁移的思想内核 | 抽离语境后能套用到任意同类工具的那条原则 |

**硬约束：**

- 与借鉴裁决**严格解耦**：本阶段禁止出现 ✓/✗/~、禁止"soso-kit 已有/缺失"的判断、禁止"是否该做"的结论。那些一律留给 Phase 6.5/6.6。
- 每条亮点附目标项目 `file:line`；这是对**目标项目代码**的取证（区别于 Phase 6.5 对 soso-kit 代码的取证）。
- 宁缺毋滥：只收"够格"的机制，平庸实现不入选；但若项目确有多个亮点，不得为压缩而漏报，可归类聚合。
- 若穷尽后确无够格机制，如实输出「无突出亮点机制」，**禁止为凑数硬留平庸项**（与 Phase 6.5「禁止凑数硬留」对称）。
- 评判维度可参考但不限于：交互范式、质量/可信度的量化或分级、闸门与降级策略、上下文/token 纪律、扩展点与解耦、可复现性。**示例仅为启发，不得点名任何具体外部项目。**

## Phase 6.5: 反向验证闸（强制，零假设 = 不借鉴）

第一性原理：每条借鉴建议默认成立的零假设是「**不借鉴**」，只有 soso-kit 源码证据能推翻它。

对 Phase 6 的**每一个**候选借鉴点，回 soso-kit 源码反证：

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
# 示例：候选='文档防漂移门禁' → 先查 soso-kit 是否已有等价机制 / 是否真存在漂移
grep -rn "<关键能力关键词>" "$KIT_ROOT/.claude/commands" "$KIT_ROOT/.claude/kit"
```

逐条回答三问（每条都要 soso-kit 源码行号，或「实测不存在」的命令输出）：

| 验证问 | 通过条件 | 不通过则 |
|--------|---------|---------|
| a. soso-kit 是否已有等价物？ | grep 无等价实现，能指向缺失证据 | 已有 → 判 ✗（重复造轮子），删除该候选 |
| b. 这是不是真问题？（真会漂移 / 真缺失 / 真痛点） | 有源码行号或实测输出证明问题真实存在 | 伪需求 → 判 ✗，删除该候选 |
| c. 是核心提升还是边际/过度设计？ | 触及核心逻辑/原理/数据结构，且收益 > 成本 | 仅边际或成本超收益 → 降级 ~，或对单人/本地工具链场景判过度设计 → ✗ |

**硬约束：**

- 任何 `✓` / `~` 建议必须在文档里附 soso-kit 源码 `file:line`（证明缺失）或实测命令输出。拿不出 → 标 `[推理]` 并降级，或直接删除。
- 对齐 constitution「证据落地」：找不到行号的判断标 `[推理]` 或回去补读。「听起来该有 / 通常 / 可能」是反模式。
- 验证后若所有候选都被否，如实输出「无值得借鉴点」，**禁止为凑数硬留**。

**A.「核心流程」节**（三段式，HARD-GATE）：

> ⛔ **HARD-GATE：须按「① 流转全景 → ② 速查表 → ③ 展开图」三段依次呈现**（每段前配一句串场文案），全 ASCII、不依赖 Mermaid、**禁止用文字列表代替**。模板该节已内置三段骨架，按项目实况填充。默认 ① 横向全景（`─▶`）、③ 纵向管道（`╔══╗`）；项目是状态机可把 ① 换顶层状态机框（`┌──┐`）、多分支把 ③ 换分路径。校验三段缺一即未通过：① 有一张流转图（横向链或状态机框，含箭头 / 框线）；② 有一张 ≤3 列 markdown 表（含 `|---|` 分隔行，首列名按项目可为命令/模块/单元）；③ 有一张展开图（纵向管道 `╔══╗` 或分路径）。任一缺失 → 回填后再输出。

**C.「借鉴建议」节结构**（采用以下五问，第 0 问为零假设校验，缺一不可，禁止合并或省略）：

## Phase 8: 持久化

### 8.0 写入前自检：无内部工具链痕迹（强制）

研究文档可能被跨团队 / 跨项目 / 未来的自己阅读，**禁止**残留 soso-kit 命令名或 AI 工具链关键词。

写入前 grep 全文：

```
/k:|subagent|Claude|Cursor|AI[^a-zA-Z]|双闸门
```

任何命中 → 改中性表述后再写入（如「`/k:debug-on` 实测」→「已运行时验证」；「subagent 复核」→「独立复核」）。

### 8.1 写入文档

使用 Write 工具将完整研究文档写入：

```
$KIT_ROOT/.claude/kit/study/output/<PROJECT_NAME>.md
```

如果文件已存在（重复 study）：
- 覆盖主体内容
- 在 `## 变更记录` 末尾追加新条目：`- <今天日期>: 更新分析`

### 8.2 更新 Registry

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/study/scripts/save-study.sh" \
    --name "<PROJECT_NAME>" \
    --repo "<REPO>" \
    --path "<LOCAL_PATH>" \
    --commit "<COMMIT>" \
    --doc-path "$KIT_ROOT/.claude/kit/study/output/<PROJECT_NAME>.md"
```

从 JSON 输出中提取 token 统计信息。
