# Clarify: [想法主题]

## 用户输入

```text
$ARGUMENTS
```

---

## 核心目的

通过结构化对话将模糊想法转化为明确的设计方案，生成符合 spec 标准的文档供 `/k/spec` 自动加载使用。

<HARD-GATE>
设计方案未经用户批准前，不得写任何代码，不得调用任何实现命令。
</HARD-GATE>

---

## 执行步骤

### 0. 读取输入文档（读取脚本输出）

脚本已扫描 `.claude/kit/clarify/` 目录，根据 JSON 输出处理：

- `found: true` → 用 Read 工具读取对应 `.md` 文件内容，以此为对话起点
- `found: false` → 以 `$ARGUMENTS` 文字为起点

输出：
- 有文件 → `📄 已读取想法文档：[文件名]`
- 无文件 → `💬 将从对话输入中理解想法`

---

### 1. 探索项目上下文

- 分析当前代码库结构，识别相关模块
- 找出可复用的组件 / 模式 / 约束
- 输出：`🔍 项目上下文：[关键发现 2-3 条]`

**Context 轻量提示（默认行为）**：

分析项目结构时顺手扫一眼 `.claude/kit/context/library/<project>/context-index.json`（若存在）。若发现明显相关功能（关键词字面命中或语义近似），在项目上下文输出中追加一行：

```
💡 历史参考：<context-id> 可能与此相关，可在 /k:spec 阶段加载
```

> 仅提示，**不主动加载**、**不要求用户确认**、**不影响 spec 文档**。Context 搜索的主入口在 `/k:spec`。

**显式触发（可选）**：`$ARGUMENTS` 含 `--c <keyword>` 时，调用 preflight 脚本主动搜索：

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/spec/scripts/context-preflight.sh" "$ARGUMENTS"
```

展示候选供本次澄清参考即可。spec 阶段仍会重新搜索（关键词更明确，命中率更高），不需要在 spec 文档中写标记。

---

### 1.5 提问前心态（Think Before Coding）

> 进入分层提问前，对 Step 2 的模糊度评估作两条附加要求。与后续 Step 2/Step 6 不重复，仅补事前心态。

| 检查项 | 说明 |
|--------|------|
| **简化机会主动提** | 若识别到比需求更简单的已有方案（现有 hook / 组件 / 流程可复用），**第一轮就说**，不等用户发现 |
| **困惑即命名** | 不清楚的点必须显式命名，禁止"猜着往下做"或把 TBD 塞进 spec 留给下游 |

---

### 2. 分层提问澄清（最多 8 问）

> 每次只问一个问题，不得同时抛出多个。优先使用选择题，每个问题附上推荐答案和理由。

**输出格式（Q 样式：编号 + 缩进，与 /k:spec 反问统一）**：

普通题：
```
📍 问题 N/总数 · [维度]

  1. [问题内容]
       推荐 → [推荐答案]
       理由 → [基于哪个证据 / 上下文判断]
```

选项题：
```
📍 问题 N/总数 · [维度]

  2. [问题内容]
       A. [选项 A]
       B. [选项 B]
       C. [选项 C]
       推荐 → [A/B/C]
       理由 → [基于哪个证据 / 上下文判断]
```

> 子项缩进 4 格，与 `/k:spec` 反问的选项 ABC 缩进一致。
> 不用 ┃ 双栏——区别于"AI 表述类"（需求理解等）。

**必问 2 个（每次都问，顺序固定）：**

| # | 问题 | 维度 |
|---|------|------|
| Q1 | 核心用户场景是什么？用户从哪里触发，完成什么目标？ | 用户场景 |
| Q2 | 什么情况下算完成？验收标准是什么？ | 成功指标 |

**核心问 4 个（从下表选最模糊的维度，跳过已经清晰的）：**

| # | 问题 | 维度 | 何时问 |
|---|------|------|--------|
| Q3 | 有哪些明确不做的？边界在哪里？ | 排除项 | 需求范围模糊时 |
| Q4 | 数据从哪来、存哪里？有哪些核心实体？ | 数据模型 | 涉及数据存储/流转时 |
| Q5 | 依赖哪些外部系统或接口？ | 集成 | 有第三方或跨模块依赖时 |
| Q6 | 有错误或异常场景需要特别处理吗？ | 错误处理 | 有明显失败路径时 |

**可选问 2 个（复杂需求才追加，明确告知用户"可跳过"）：**

| # | 问题 | 维度 |
|---|------|------|
| Q7 | 有性能、安全或兼容性要求吗？（NFR = 非功能性需求，如响应时间、权限控制） | NFR |
| Q8 | 如果分阶段交付，哪个必须先上，哪个可以后做？ | 优先级 |

**提问规则：**
- 必问 2 个无条件提问
- 核心 4 个中，评估模糊度后选 0-4 个提问（已经清晰的跳过）
- 可选 2 个：需求复杂度高才追加，提问时注明"这是可选问题，可以跳过"
- 总上限 8 个，不超
- **追问不计入数量**：若用户回答中引入新信息（如提到"加分页"），可在下一轮追问细节（如"每页几条？"），追问不占用 8 问配额
- **进度显示**：每次提问前显示当前进度，格式为 `📍 问题 N/总数`，其中"总数"为本次预计提问总数（开始前预估，中途可随理解深入调整）

---

### 3. 方案对比

结合项目上下文和对话结论，提出 2-3 个方案：

| 方案 | 思路 | 优点 | 缺点 | 改动量 | 风险 |
|------|------|------|------|--------|------|
| 方案 A | ... | ... | ... | 小/中/大 | 低/中/高 |
| 方案 B | ... | ... | ... | 小/中/大 | 低/中/高 |
| 方案 C | ... | ... | ... | 小/中/大 | 低/中/高 |

**推荐**：[方案 X]

**推荐理由**（按优先级）：
1. 改动少
2. 副作用小
3. 稳定性好
4. 可维护性强

---

### 4. 增量设计确认

用户选定方案后，分节展示设计，**每节等待用户确认再继续**：

1. **架构 / 整体方案** — 确认方向正确
2. **核心数据结构 / 逻辑** — 确认关键设计
3. **边界情况 / 错误处理** — 确认覆盖范围
4. **与现有代码的集成点** — 确认影响范围

如用户提出修改 → 回到对应节重新设计，不跳过。

---

### 5. 生成 Spec 文档

用户完整批准设计后，执行脚本创建规范文件：

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/clarify/scripts/spec-create.sh" "<topic-slug>"
```

> `<topic-slug>` 为本次功能的英文简短描述，如 `dark-mode`、`user-auth`

脚本输出格式：
- `CREATED:/path/to/file.md` → 记录路径，填入设计内容
- `ALREADY_EXISTS:/path/to/file.md` → 读取已有文件，追加或更新内容

**填写文档时必须包含以下章节（缺一不可）**：

| 章节 | 内容要求 |
|------|----------|
| 背景与目的 | 清晰说明为什么做，解决什么问题 |
| 选定方案 | 说明选择了哪个方案及核心理由 |
| 设计概要 | 架构思路、核心逻辑、关键数据结构 |
| 边界与约束 | 明确包含 / 不包含 / 已知限制 |
| 集成点 | 列出涉及的现有文件 / 模块 / API |
| 验收标准 | 可执行的 checklist，每项可独立验证 |
| 验收场景 | Given/When/Then 格式，每个用户故事至少 2 个场景（见格式要求） |

**验收场景格式要求**：

```markdown
## 验收场景

### 场景 1：[Happy Path 名称]
- **Given** [具体前置状态：数据条件 + 系统状态 + 用户状态，必须含具体数值]
- **When**  [单一操作，不含多步骤]
- **Then**  [可独立验证的结果：UI 变化 / 数据变化 / 状态变化，至少一类]

### 场景 2：[边界或异常名称]
- **Given** [前置状态]
- **When**  [触发条件]
- **Then**  [预期结果]
```

> **Given 质量标准**：不能写「用户已登录」（太模糊），要写「用户钱包已连接，ETH 余额 > 0.01，当前网络 = Arbitrum」

---

### 6. 文档自检（HARD GATE）

> ⚠️ 全部通过才能流转，任意一项 ❌ 必须先修复文档再重新自检

**6.0 工序级结构 lint（强制，先跑后输出自检表）**：

```bash
KIT_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
bash "$KIT_ROOT/.claude/kit/clarify/scripts/spec-lint.sh" "<spec 文件绝对路径>"
```

输出规则：
- `✅ 0 问题` → 静默通过，继续 6.1 逻辑核查
- 有 ⚠️ → 必须先修复文档再重跑，全绿才能进入 6.1

> **原则依据**：见 `.claude/kit/principles/strict-vs-cumbersome.md` §4.3 正 pattern「工序失败时才生成输出」

**6.1 逻辑核查（强制逐项输出）**：

| 检查项 | 标准 | 状态 |
|--------|------|------|
| **结构完整** | 包含全部 7 个必要章节，无占位符未替换 | ✅/❌ |
| **需求清晰** | 目标 / 边界 / 验收标准表述无歧义 | ✅/❌ |
| **方案一致** | 文档内容与对话中用户确认的结论完全一致 | ✅/❌ |
| **无幻觉** | 未添加对话中未讨论的功能、假设或细节 | ✅/❌ |
| **验收可测** | 验收标准是可独立执行的 checklist，非模糊描述 | ✅/❌ |
| **场景具体** | 验收场景 Given 含具体数值/状态，Then 可独立验证，每个用户故事 ≥ 2 个场景 | ✅/❌ |

**自检输出格式（与 /k:check 表格样式统一）**：

PASS 路径：
```
🔍 文档自检

| 检查项     | 状态 | 说明 / FAIL 时的位置                |
|------------|------|-----------------------------------|
| 结构完整   |  ✅  | 7 章节齐全                          |
| 需求清晰   |  ✅  | 目标/边界/验收无歧义                |
| 方案一致   |  ✅  | 与对话第 N 轮确认一致               |
| 无幻觉     |  ✅  | 未引入未讨论内容                    |
| 验收可测   |  ✅  | N 条 checklist 可独立验证          |
| 场景具体   |  ✅  | 场景 Given 含具体数值              |
```

FAIL 路径（说明列变为 file:line + 一句话修复点）：
```
🔍 文档自检

| 检查项     | 状态 | 说明 / FAIL 时的位置                |
|------------|------|-----------------------------------|
| 结构完整   |  ❌  | 缺"集成点"章节                      |
| 需求清晰   |  ✅  |                                   |
| 场景具体   |  ❌  | 场景 1 Given 写"用户已登录"（缺具体状态）|
```

## 完成条件（Card A 直角单卡）

> 仅在「设计方案已批准 + 文档自检全 ✅」后输出。任一未满足 → 不输出本节。

```
┌─ ✅ Clarify 完成 ──────────────────────────────┐
│                                                │
│  📄 spec 文档                                  │
│     .claude/kit/spec/YYYY-MM-DD-<topic>.md    │
│                                                │
│  🎯 选定方案                                   │
│     [方案名]：[一句话方案概要]                 │
│                                                │
│  📋 核心决策（N 项）                           │
│     · [决策 1]                                 │
│     · [决策 2]                                 │
│     · [决策 3]                                 │
│                                                │
│  🔀 下一步 → /k:spec 加载该文档                │
│                                                │
└────────────────────────────────────────────────┘
```

**格式规则**：
- 卡片宽度统一约 50 字符（含 `│` 和内边距）
- 标题行 `┌─ ✅ Clarify 完成 ─...─┐` 用 `─` 填充对齐
- 每段内容前后保留空 `│  │` 行（提供呼吸感）
- 内容文本缩进 2 格（含 emoji 锚点）
- 字段名独占一行，下方缩进 5 格（emoji 后对齐）展开内容
- 核心决策子项用 `· ` 项目符号
- 长路径允许超出右边框（不强制换行）
- 关于宽度过窄场景：终端 < 60 字符宽时仍保留卡片结构（用户自行处理换行）

> 样式参考：`docs/cli-output/decision-output-template.md` §D 卡片式

## 📌 说明

**适用场景**：想法模糊 / 还没想清楚要做什么 / 需要方案对比后再决策

**输入文档**：`.claude/kit/clarify/` 放粗糙想法笔记（可选，不放则从对话开始）

**输出文档**：`.claude/kit/spec/YYYY-MM-DD-<topic>.md`（被 `/k/spec` Step 0 自动加载）
