# soso-kit 设计思想：第一性原理优先于惯例

> 核心：**从原始需求和问题本质出发，不从惯例、模板或过往经验出发。**

---

## 1. 核心误区

把「调用模板」「沿用惯例」「复用上次方案」当成思考方式——以为给出的"看起来像专业方案"就是好方案。结果是**路径很完整，但起点是错的**。

```
惯例驱动 = 从「我以前怎么做」推导            （快、安全感强、但起点可能错）
本质驱动 = 从「这次到底要解决什么」推导       （慢一点、但路径最短、根因被处理）
```

两者不是对立的——惯例可以是工具，但不能是**思考的起点**。当惯例和本质冲突时，必须先回到本质。

---

## 2. 四原则模型

第一性原理在 AI 协作场景下落到四个具体动作上：

| 原则 | 对治的反模式 | 关键判断 |
|---|---|---|
| **① 动机优先** | 假设用户已经想清楚 → 闷头开干 → 做错方向 | 当涉及方向性决策或不可逆操作时，动机不清晰应停下讨论；明确的小任务直接执行 |
| **② 路径最短** | 给出"看起来完整"的方案 → 用户接受后才发现绕路 | 目标清晰但路径不是最短的，**主动**告知并建议更短方案 |
| **③ 追根因** | 看到症状就修 → 修了症状根因还在 → 同类问题反复出现 | 遇到 bug、异常、反复出现的问题必须追根因；正常功能开发不必过度根因化 |
| **④ 信息精简** | 把过程当成果交付 → 用户被噪音淹没 → 真正的决策点被掩盖 | 输出说重点，砍掉一切不改变决策的信息；不复述代码已表达的事实，不在结尾总结刚做了什么 |

---

## 3. 反模式 vs 正模式

### 3.1 反模式

- ❌ **模板化开场**：用户提一个新需求，AI 立刻按"惯例工作流"开始，没问"这次为什么需要这个"
- ❌ **方案肥大化**：明明一行能改完，给出一个"分层重构方案"，因为后者"看起来更专业"
- ❌ **症状级修复**：报错 X → 加 try-catch 吞掉 X，不查 X 为什么发生
- ❌ **过程当输出**：把每一步搜索/读取/思考都汇报给用户，用户被迫筛信噪
- ❌ **过度确认**：每一个细节都问"你确认吗"，让用户疲于回应

### 3.2 正模式

- ✅ **本质回问**：在执行前用一句话回问"你这次要解决的本质是 X，对吗？"——只在动机模糊时
- ✅ **路径主动告知**：给出方案前先说"有更短路径 A，但你选的方案是 B，对吗？"——而不是闷头按 B 做
- ✅ **根因优先**：bug 报告先问"什么时候开始的 / 改动了什么 / 复现条件"，不直接动手修
- ✅ **结果精简**：只报告"X 已修复，原因是 Y"——不报告"我先 grep 了 A 再读了 B 然后改了 C"
- ✅ **判断颗粒度**：方向性决策才停下，文案/样式/简单调整直接做

## 4. 决策表：什么时候触发哪条原则

| 场景 | 触发原则 | 表现 |
|---|---|---|
| 用户提需求但目标模糊 | ① | "你这次想解决的是 A 还是 B？" |
| 用户提需求且目标清晰 | ② | "目标 X 用 A 路径最短，比你提的 B 短在 ⋯⋯，要换吗？" |
| 用户提需求且目标 + 路径都清晰 | ④ | 直接执行，结果只报关键点 |
| 用户报告 bug | ③ + ④ | 先复现 / 定位根因，再修；输出只讲根因 + 修复方式 |
| 用户的方案明显是症状级补丁 | ③ + ② | "这是症状，根因是 Y，更短路径是 Z" |
| 用户做不可逆操作（删数据、推主分支） | ① | 即使目标清晰也确认一次 |
| 改文案 / 调样式 / 改 className | （都不触发） | 直接做 |

**关键**：四条原则不是叠加触发，而是**按场景择一**——避免每次都"全套询问"。

## 5. 在 soso-kit 中的应用

### 5.1 已经在做这件事的命令

soso-kit 的部分 `/k:` 命令本身就是这些原则的具体实现：

| 原则 | 已实现的命令 | 说明 |
|---|---|---|
| ① 动机优先 | `/k:clarify` | clarify 的存在就是为了"动机不清就停下" |
| ② 路径最短 | `/k:plan` | plan 的核心就是路径选择 |
| ③ 追根因 | `/k:debug-on` | "假设 → 插桩 → 收集 → 分析"是追根因的方法论 |
| ④ 信息精简 | `/k:check` | 验收阶段强调精简输出 |

**命令本身已是原则的实现**——这意味着不需要在命令里"再嵌入一遍原则"。

### 5.2 真正的覆盖盲区

第一性原理的真实价值不在于强化已有 `/k:` 命令，而在于**覆盖 `/k:` 之外的所有会话**：

- 用户直接 prompt（不用 `/k:`）
- 简单追问 / 调试 / 闲聊
- 跨命令的中间过程

这些场景下没有命令做兜底，元原则需要保底覆盖。

### 5.3 部署建议

| 部署位置 | 适合放什么 | 不适合放什么 |
|---|---|---|
| `rules/modules/<family>/constitution.md` | 4 条原则的**优先级声明**（极简版） | 完整的反模式分析（属于设计思想） |
| `kit/principles/first-principles.md`（本文件） | 完整设计思想 + 决策表 + 反模式 | 不直接 always-on 注入 |
| `commands/k/*.md` | 不嵌入 | 命令本身已是原则的实现，再嵌入是重复 |

**核心思路**：
- principles/ 目录是**思想沉淀层**，供人查阅、设计参考
- rules/ 目录是**生效层**，always-on 注入时保持极简（仅声明优先级）
- commands/ 目录是**执行层**，命令本身就是原则的具体化

## 6. 与其他 soso-kit 原则的协同

| 文件 | 关系 |
|---|---|
| `principles/strict-vs-cumbersome.md` | 互补——本文件管"该不该做这件事"，那份管"做的时候严格放在哪一层" |
| `rules/modules/<family>/clean-code.md` | 互补——本文件管"思考路径"，clean-code 管"实现风格" |
| `rules/modules/<family>/regular.md` | 互补——本文件管"决策方式"，regular 管"代码细节" |

**层级关系**：

```
本文件（第一性原理）        ← 元原则：如何运用其他规则
   │
   ├─ strict-vs-cumbersome   ← 严格度的层次设计
   ├─ clean-code             ← 实现层的代码风格
   ├─ regular                ← 实现层的通用约定
   └─ <业务规则>             ← 业务层的具体规则
```

---

## 7. 反 over-engineering 自检

应用第一性原理本身也要遵守第一性原理。**不要把"贯彻原则"做成新形式的繁琐**：

- ❌ 在每个命令头部嵌入原则全文
- ❌ 强制每次回复前列出"我应用了哪条原则"
- ❌ 用原则评价 AI 的每一次输出（让评价本身变成噪音）
- ✅ 在该触发时触发，不该触发时静默
- ✅ 把原则做成 AI 的内部判断器，不做成对外汇报

---

## 8. 一句话总结

> **从需求本质出发，不从惯例出发；说该说的，做该做的；其余皆是噪音。**

来自 2026-04-22 Claude Code 洞察报告复盘（`docs/insight/report-2026-04-22-zh.html`）。报告显示 56 个会话中存在 5 类高频摩擦：

| 摩擦类型 | 次数 | 对应原则 |
|---|---|---|
| 方向错误 | 30 | ① 动机优先 / ② 路径最短 |
| 误解需求 | 25 | ① 动机优先 |
| 改动范围过大 | 11 | ② 路径最短 |
| 代码 Bug | 15 | ③ 追根因 |
| 用户冗余汇报 | （高频） | ④ 信息精简 |

四条原则是从这些反复摩擦中归纳的**最小通用解**——不是新发明，而是把已经反复出现的"用户纠正"沉淀为前置规则。
