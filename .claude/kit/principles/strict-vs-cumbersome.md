# spec-kit 设计思想：严格 ≠ 繁琐

> 核心：**工序层尽量严格，输出层保持简洁，规则层少而精。**

---

## 1. 核心误区

把「严格」和「繁琐」当成同一维度——以为"提升严格度"就必然"增加繁琐度"，于是放弃严格。这是错的。

```
严格 = 拦下错误的力度       （高严格 = 错漏少）
繁琐 = 实际承担的成本       （高繁琐 = 审查累 / token 多 / 等待长）
```

两者不是同一维度。**可以严格但不繁琐**——关键看严格放在哪一层。

---

## 2. 三层模型

| 层 | 谁承担成本 | 严格收益 | 设计原则 |
|---|---|---|---|
| **输出层**<br>（用户看到的报告 / 标注 / 对照表） | 用户审查成本 ↑↑ | 中 | **谨慎** — 越长越难审 |
| **工序层**<br>（AI 内部跑的 grep / Read / 自检 / 反向核查） | token 成本（用户不直接感知） | 高 | **追求严格** |
| **规则层**<br>（CLAUDE.md / always-on header） | 上下文占用 + 易被 skim | 中（取决于条数） | **少而精，≤5 条核心** |

---

## 3. 决策表

| 候选机制 | 严格在哪一层 | 是否值得 |
|---|---|---|
| 强制每个决策标 `[实证]/[推理]/[假设]` | 输出层 | ❌ 用户每次都要看分类标注，噪音大 |
| AI 内部跑 grep 拦跨文档矛盾，只在出问题时报告 | 工序层 | ✅ 用户只看"0 矛盾"或精确问题 |
| 强制每节自检列 18 项勾选 | 输出层 | ❌ 结构勾选 ≠ 逻辑核查，制造"已自检"假象 |
| 决策变更后 AI 自动 grep 旧决策位置 | 工序层 | ✅ 拦下"前后矛盾"问题，用户透明 |
| 8 条 always-on 详细规则 | 规则层（过载） | ❌ 越多越被 skim，无效 |
| 3 条核心规则（absence-of-evidence / 信息缺口命名 / 反 agreeable bias） | 规则层（精选） | ✅ 简单不可绕过 |
| 用户确认 Y 后强制列对比表 | 输出层 | ❌ 反 agreeable 应做成内部反问，不是输出 |
| 重大方案变更触发式 grep 工序 | 工序层（触发式） | ✅ 不是 always-on，按需启动 |

---

## 4. 设计指导

### 4.1 What goes where

```
工序层（强制严格，对用户透明）
  ├─ 跨文档一致性扫描（/k:check 内置 grep）
  ├─ 决策变更后传播工序（grep 旧关键词 → 报告残留 → 必须修）
  ├─ 信息源核查（重要决策前强制 Read 源文件，不仅看 reference）
  └─ absence-of-evidence 拦截（推理捷径在内部被打回）

规则层（少而精，always-on）
  ├─ absence-of-evidence ≠ evidence
  ├─ 信息缺口必须显式命名（不许塞 TBD）
  └─ 用户同意 ≠ 免除披露责任

输出层（保持简洁）
  ├─ 自检结果只输出"通过 / 问题清单"，不强迫每条标元数据
  ├─ 决策对比表只在多个 [推理] 决策共存时输出
  └─ grep 结果只在有矛盾时显示，无矛盾静默通过
```

### 4.2 反 pattern

- ❌ 把工序变成输出（让用户审 AI 跑过的所有 grep）
- ❌ 把规则堆成手册（8 条规则 = AI 自动 skim）
- ❌ 强制结构性标注（[实证]/[推理] 在混合决策中是噪音）
- ❌ 用结构勾选替代逻辑核查（"7 项自检 ✅" 给假象）

### 4.3 正 pattern

- ✅ 工序失败时才生成输出（"扫描了 N 处，0 矛盾" vs "扫描了 N 处，发现 X 处矛盾 + 修复建议"）
- ✅ 规则触发式（重大方案变更 → 触发 grep 传播工序，不是每次都跑）
- ✅ 元认知质疑做成内部工序（AI 自己问"我有什么不知道的"）而非输出强制

---

## 5. 应用到 spec-kit 各阶段

| 阶段 | 工序层加什么 | 输出层保持 | 规则层 |
|---|---|---|---|
| `/k:clarify` | 决策点强制 Read 源文件确认 | 决策报告简洁，不强标 [实证]/[推理] | 同 §4.1 三条 |
| `/k:spec` | 跨阶段决策一致性扫描 | 7 章节模板不变 | 同上 |
| `/k:plan` | grep 旧决策残留 + 跨文档对照 | 覆盖度对照表只列 ⚠️ 项 | 同上 |
| `/k:task` | 改完后 grep 验证 0 残留 | 任务清单不强加元数据 | 同上 |
| `/k:check` | 跨文档矛盾扫描 + 反向 grep | 18 项精简为「通过 / N 个问题」 | 同上 |

---

## 6. 一句话总结

> **AI 工程不应模仿传统软件工程的"流程繁琐"，因为 AI 的工序成本 ≠ 人的注意力成本。把严格塞进 AI 内部工序，把简洁留给用户审查——这样 spec-kit 既能拦下错误，又不会让用户嫌烦。**
