# soso-kit 设计思想：证据落地（Evidence Grounding）

> 核心：**判断不能脑补——风险/复杂度/可行性评级必须能指向具体源码行号；落不到行号的判断都是脑补。**

---

## 1. 核心误区

LLM 的默认工作方式是用**语言相似性匹配**代替**源码事实**。当被要求评估"某方案的风险"时，AI 倾向于生成"看起来专业"的判断而非"扎实读源"的判断——因为前者的 token 路径更短、更顺滑。

```
脑补评估 = 用关键词关联 + 训练数据偏置 + "听起来" 直觉      （快、便宜、错得隐蔽）
证据评估 = 读源码 + 引用具体行号 + 显式标推理              （慢、贵、错得显眼）
```

两者**最终输出形式可能一样**（都是"中风险"/"高风险"），但**支撑这个评级的事实强度差几个数量级**。

**关键判据**：

> 判断坑不坑，靠的是能否把每条风险落到具体源码行——落不到行的风险都是脑补。

---

## 2. 三类证据形式

| 形式 | 例子 | 强度 |
|---|---|---|
| **A. 源码行号** | `Dialog/index.tsx:86-91 引用计数实现` | ⭐⭐⭐⭐⭐ 最强 |
| **B. 测试/文档段落** | `useAppKit/types.ts:45 公共 API 定义` | ⭐⭐⭐⭐ 强 |
| **C. 显式推理** | `[推理] 依据：A 形式的 X.tsx:N` | ⭐⭐ 弱（但合规） |
| **D. 无引用** | "听起来要改基础设施" | ❌ 反模式（禁止） |

**核心要求**：所有评级必须满足 A/B/C 任一形式。**D 一律禁止**。

---

## 3. 反模式 vs 正模式

### 3.1 反模式（禁止）

| 反模式 | 例句 |
|---|---|
| 关键词联想 | "modal=false **听起来**要改基础设施" |
| 训练数据偏置 | "**通常**这种场景需要 portal container" |
| 模糊量词 | "**可能**会引入 race condition" |
| 单先例锚定 | "Email 入口用了 close 调用，**所以**项目偏好这种" |
| 抽象复杂度 | "复杂度高（说不出代码行）" |

### 3.2 正模式

| 正模式 | 例句 |
|---|---|
| 引用源码行 | "modal=false 路径完整（基于 `Dialog/index.tsx:86-91`）" |
| 引用类型定义 | "API 已暴露（`types.ts:45` 公共字段）" |
| 多先例对比 | "Email（`X.tsx:30`）和 Vault（`Y.tsx:20`）两处先例不一致" |
| 显式推理 | "[推理] 引用计数可能受影响，依据 `Z.tsx:50` 的实现" |
| 承认未知 | "未读完 `Dialog/index.tsx` 的 hooks 部分，需先 Read 再评级" |

---

## 4. 决策表：何时触发证据要求

| 场景 | 是否触发 | 说明 |
|---|---|---|
| 多方案对比时的成本/风险评级 | ✅ 强触发 | 评级直接影响选型，必须配证据 |
| 单方案的"安全性/影响面"评估 | ✅ 强触发 | 同上 |
| Bug 假设的可能性排序 | ✅ 触发 | 假设需要证据支撑 |
| 复杂度估算（高/中/低） | ✅ 触发 | 估算 = 评级 |
| 改文案 / 调样式 / 简单重命名 | ❌ 不触发 | 不涉及评级 |
| 技术问题的概念解释 | ❌ 不触发 | 不涉及对项目代码的判断 |

---

## 5. AI 评估失效的可识别信号

用户在协作中可识别以下信号 → 触发追问"能给个 file:line 吗"：

| 失效信号 | 说明 |
|---|---|
| 评级形容词无引用 | "中风险" 后没有 `(基于 ...)` |
| 用"听起来"/"通常"/"可能" | 关键词联想代替源码核查 |
| 单先例就成立判断 | "X 处用了 A，所以项目偏好 A" — 没找第二例 |
| 说不出"哪一步要写代码" | 抽象复杂度 = 脑补 |
| 评估快得不合理 | 没看到 Read 工具调用就给结论 |

**用户协作要点**：看到 file:line 时**抽查一两次**——确认存在 + 确认相关。AI 知道用户会查后，糊弄式合规会下降。

---

## 6. 自检触发规则

AI 在输出方案对比 / 风险评级时，每条结论交付前自问：

```
1. 我能引用 file:line 吗？
   ├─ 能 → 写出来
   └─ 不能 → 是基于推理还是脑补？
        ├─ 推理 → 标 [推理]，写出依据
        └─ 脑补 → 回去 Read 相关源码，不要硬给评级
```

## 7. 在 soso-kit 中的应用

### 7.1 已经做对的命令

| 命令 | 现状 | 说明 |
|---|---|---|
| `/k:debug-on` | ✅ 输出格式已用 `Code Path: file:line → file:line` 和 `P1: file:line — log <expr>` | 调试假设和插桩点天然带行号 |
| `/k:check` | ✅ CHK-04c 已做 absence-of-evidence 核查 | 事后核查机制 |

### 7.2 需要补的命令

| 命令 | 缺口 | 已落地补丁 |
|---|---|---|
| `/k:plan` | 风险自审存在但未要求证据列 | L283 区域已加证据格式约束（v1.2.0） |

### 7.3 兜底机制

`rules/modules/<family>/constitution.md` 第一性原理第 5 条 always-on，覆盖：
- /k 之外的日常会话
- 非 plan 阶段的临时评估
- 所有规则未明确覆盖的场景

## 8. 与其他原则的关系

| 原则 | 关系 |
|---|---|
| 第一性原理 ② 路径最短 | **互补**——路径最短要求"主动告知更短路径"，证据落地确保这个判断本身扎实 |
| 第一性原理 ③ 追根因 | **互补**——根因必须基于证据，否则是症状级修复 |
| 严格 ≠ 繁琐 §4.1 工序层 | **同源**——工序层"决策点强制 Read 源文件"是证据落地的具体落地 |
| Clean Code | 正交 |

**层级**：

```
思考起点    → 第一性原理（不从惯例出发）
判断品质    → 证据落地（每个判断要有源码支撑）  ← 本文件
严格度分配  → 严格 ≠ 繁琐（严格放工序，简洁放输出）
```

---

## 9. 反 over-engineering 自检

- ❌ 给所有输出都强加 file:line（包括根本不涉及评级的内容）
- ❌ 强行凑无关引用满足格式（糊弄式合规）
- ❌ 把所有 [推理] 都视为同等弱——推理本身有依据时仍是合法证据
- ✅ 只在评级类判断触发
- ✅ 真不知道时承认"未读完，需先 Read"，比硬凑引用更好

---

## 10. 已知局限

- LLM 可能学会"列假证据"——糊弄式合规规则本身无法识别
- 用户必须**抽查 file:line 是否真存在 + 真相关**，否则机制失效
- 第 5 条与第 ③ 条"日常开发不过度根因化"在边界场景可能轻微冲突——观察 2-3 次实战后调整

---

## 11. 一句话总结

> **每条评级配源码行；写不出行号的，要么标 [推理]，要么回去补读。**
