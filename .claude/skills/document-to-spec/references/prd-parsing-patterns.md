# PRD 解析模式参考

识别和提取 PRD 文档中的关键信息的常见模式。

---

## 常见 PRD 结构模式

### 模式 1: 标准 PRD 结构

```markdown
# [功能名称] PRD

## 1. 背景和目标
- 问题陈述
- 目标用户
- 业务价值

## 2. 用户故事
- As a [user]...

## 3. 功能需求
- 功能列表
- 优先级

## 4. 验收标准
- 成功标准

## 5. 技术要求
- 性能要求
- 安全要求
```

**提取策略**:
- 背景和目标 → Spec 概述
- 用户故事 → 直接映射
- 功能需求 → 分类为 MUST/SHOULD/MAY
- 验收标准 → 整合到用户故事中
- 技术要求 → 转换为功能需求（非技术实现）

---

### 模式 2: 一页式 PRD

```markdown
## 问题
[2-3 句话]

## 解决方案
[核心功能列表]

## 成功指标
[KPI]

## 范围
In: [功能 A, B, C]
Out: [功能 X, Y]
```

**提取策略**:
- 问题 → Spec 概述
- 解决方案 → 用户故事 + 功能需求
- In/Out → 确定优先级和边界

---

### 模式 3: Agile Epic 格式

```markdown
Epic: [功能名称]

## Goals
- Goal 1
- Goal 2

## User Stories
| ID | Story | Priority | Points |
|----|-------|----------|--------|
| US-001 | ... | P0 | 5 |

## Acceptance Criteria
- [ ] Criterion 1
- [ ] Criterion 2
```

**提取策略**:
- Goals → Spec 概述
- User Stories → 直接映射，转换优先级（P0→P1🎯MVP）
- Acceptance Criteria → 分配到各用户故事

## 关键信息识别模式

### 1. 用户故事识别

#### 模式 A: 标准格式

```
As a [role]
I want [action]
So that [benefit]
```

**正则匹配**:
```regex
As a (.+?)\s+I want (.+?)\s+So that (.+)
```

**提取示例**:
```
输入: "As a user I want to reset my password So that I can regain access"
输出:
  角色: user
  操作: reset my password
  价值: regain access
```

#### 模式 B: 中文格式

```
作为[角色]，我想要[操作]，以便[价值]
```

**正则匹配**:
```regex
作为(.+?)，我想要(.+?)，以便(.+)
```

#### 模式 C: 列表格式

```
- 用户可以 [操作]
- 系统应该 [行为]
```

**关键词识别**:
- "可以"、"能够" → 用户能力
- "应该"、"必须" → 系统行为
- "需要"、"想要" → 用户需求

---

### 2. 功能需求识别

#### 模式 A: 编号格式

```
FR-001: [需求描述]
REQ-001: [需求描述]
```

**正则匹配**:
```regex
(FR|REQ|F)-(\d+):\s*(.+)
```

#### 模式 B: 优先级标记

```
[P0] [需求]
[Must Have] [需求]
[Critical] [需求]
```

**优先级映射**:
```
P0, Must Have, Critical → MUST
P1, Should Have, Important → SHOULD
P2, Nice to Have, Optional → MAY
```

#### 模式 C: 描述性列表

```
核心功能:
- 功能 A
- 功能 B

增强功能:
- 功能 C
```

**章节标题关键词**:
```
核心、必须、关键 → MUST
重要、应该 → SHOULD
可选、增强、未来 → MAY
```

---

### 3. 验收标准识别

#### 模式 A: Given-When-Then

```
Given [前置条件]
When [触发动作]
Then [预期结果]
```

**转换为 Spec 格式**:
```
当 [条件] 时，[预期结果]
```

#### 模式 B: 检查清单

```
- [ ] 验收条件 1
- [ ] 验收条件 2
```

**直接提取**: 保持原格式

#### 模式 C: 表格格式

```
| 场景 | 输入 | 预期输出 |
|------|------|---------|
| 正常登录 | 正确密码 | 跳转首页 |
| 错误密码 | 错误密码 | 显示错误 |
```

**转换为条件句**:
```
- [ ] 当输入正确密码时，跳转首页
- [ ] 当输入错误密码时，显示错误提示
```

---

### 4. 成功指标识别

#### 模式 A: KPI 表格

```
| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 转化率 | 40% | 60% |
```

**直接提取**: 保持表格格式

#### 模式 B: 性能要求

```
- 响应时间 < 500ms
- 并发支持 1000 用户
- 可用性 99.9%
```

**识别关键词**:
```
响应时间、延迟、RT → 性能指标
并发、TPS、QPS → 容量指标
可用性、正常运行 → 可靠性指标
```

#### 模式 C: 用户行为目标

```
- 用户在 2 分钟内完成注册
- 90% 的用户完成首次购买
```

**识别模式**:
```regex
\d+\s*(分钟|秒|小时)内\s*完成
\d+%\s*的用户
```

## 边界情况推导

PRD 通常不完整，需要根据功能类型推导边界情况。

### 推导规则表

| 功能类型 | 常见边界情况 |
|---------|-------------|
| **登录/认证** | • 密码错误<br>• 账户锁定<br>• Session 过期<br>• 并发登录 |
| **数据输入** | • 特殊字符<br>• 超长输入<br>• SQL 注入<br>• XSS 攻击 |
| **文件上传** | • 文件过大<br>• 格式错误<br>• 存储满<br>• 上传中断 |
| **支付/交易** | • 余额不足<br>• 重复支付<br>• 网络超时<br>• 订单并发 |
| **搜索/查询** | • 无结果<br>• 超时<br>• 特殊字符<br>• 大量结果 |
| **实时通信** | • 网络断开<br>• 消息丢失<br>• 延迟过高<br>• 并发消息 |

### 自动推导逻辑

```python
def infer_edge_cases(功能类型, 核心操作):
    边界情况 = []
    
    # 通用边界情况
    边界情况.append("当网络请求超时时？")
    边界情况.append("当用户重复提交时？")
    
    # 特定类型边界情况
    if "登录" in 核心操作 or "认证" in 核心操作:
        边界情况.append("当连续多次登录失败时？")
        边界情况.append("当 Session 过期时？")
    
    if "输入" in 核心操作 or "提交" in 核心操作:
        边界情况.append("当输入特殊字符时？")
        边界情况.append("当输入超长文本时？")
    
    if "上传" in 核心操作:
        边界情况.append("当文件超过大小限制时？")
        边界情况.append("当存储空间不足时？")
    
    return 边界情况
```

## 章节优先级识别

根据章节标题和内容，判断重要性。

### 高优先级章节

**标题关键词**:
```
问题、背景、目标、需求、功能、用户故事、
验收、标准、成功、指标、范围

problem, background, goal, requirement, feature,
user story, acceptance, criteria, success, metric, scope
```

**内容特征**:
- 包含编号列表（FR-001, US-001）
- 包含表格（需求表、指标表）
- 包含"必须"、"应该"等优先级词汇

### 低优先级章节

**标题关键词**:
```
附录、参考、技术细节、实现方案、历史记录

appendix, reference, technical, implementation, history
```

**内容特征**:
- 详细技术架构图
- 代码示例
- 历史版本说明

## 实际解析示例

### 示例 1: 解析标准 PRD

**输入 PRD 片段**:
```markdown
## 背景
当前系统缺少用户认证功能，导致无法区分不同用户。

## 功能需求

### 核心功能
- FR-001 [P0]: 用户可以使用邮箱和密码登录
- FR-002 [P0]: 用户可以使用邮箱注册新账户
- FR-003 [P1]: 用户可以重置忘记的密码

### 增强功能
- FR-004 [P2]: 用户可以使用 Google OAuth 登录

## 验收标准
- 当用户输入正确凭据时，2 秒内完成登录
- 当密码错误时，显示明确的错误提示
```

**解析结果**:
```json
{
  "概述": "为用户提供邮箱登录和注册功能，实现用户身份识别和管理",
  "用户故事": [
    {
      "标题": "邮箱登录",
      "优先级": "P1",
      "MVP": true,
      "场景": "作为已注册用户，我想要使用邮箱和密码登录，以便访问我的账户",
      "验收": [
        "当用户输入正确凭据时，2 秒内完成登录",
        "当密码错误时，显示明确的错误提示"
      ]
    }
  ],
  "功能需求": {
    "MUST": ["FR-001", "FR-002"],
    "SHOULD": ["FR-003"],
    "MAY": ["FR-004"]
  }
}
```

## 解析流程总结

```
1. 文档结构识别
   ├─ 检测 PRD 类型（标准/一页式/Epic）
   ├─ 提取章节标题
   └─ 判断章节优先级

2. 关键信息提取
   ├─ 用户故事匹配
   ├─ 功能需求分类
   ├─ 验收标准提取
   └─ 成功指标识别

3. 边界情况推导
   ├─ 根据功能类型推导
   ├─ 识别 PRD 中的异常场景
   └─ 补充常见边界情况

4. 映射到 Spec 格式
   ├─ 填充 spec-template.md
   ├─ 调整格式和语言
   └─ 补充缺失章节
```

## 常见挑战和解决方案

### 挑战 1: PRD 结构混乱

**表现**: 章节无序、信息分散

**解决**:
1. 使用关键词识别，而非依赖章节标题
2. 全文搜索"用户故事"、"需求"等关键词
3. 手动提示用户确认提取结果

### 挑战 2: 缺少验收标准

**表现**: 只有功能列表，无验收条件

**解决**:
1. 根据功能需求推导基本验收标准
2. 使用模板填充（"当...时，..."）
3. 标记为"待补充"，提示用户审核

### 挑战 3: 优先级不明确

**表现**: 所有功能都标记为"重要"

**解决**:
1. 询问用户 MVP 范围
2. 根据关键词推导（"核心"→MUST）
3. 默认前 2-3 个功能为 P1 + MVP

## 快速参考

### 关键词优先级映射

| PRD 关键词 | Spec 优先级 |
|-----------|------------|
| P0, Must, Critical, 核心 | P1 🎯 MVP + MUST |
| P1, Should, Important, 重要 | P1/P2 + SHOULD |
| P2, Nice to have, 可选 | P3 + MAY |

### 章节映射速查表

| PRD 章节 | Spec 章节 | 处理方式 |
|---------|----------|---------|
| 背景/问题 | 概述 | 提炼为一句话 |
| 目标/价值 | 概述 | 合并到概述中 |
| 用户故事 | 用户故事 | 直接映射 |
| 功能列表 | 功能需求 | 分类为 MUST/SHOULD/MAY |
| 验收标准 | 用户故事的验收 | 分配到各故事 |
| KPI/指标 | 成功指标 | 提取表格 |
| 技术方案 | ❌ 忽略 | Spec 不包含技术细节 |
