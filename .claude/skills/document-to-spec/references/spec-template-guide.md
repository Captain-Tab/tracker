# Spec 模板填写指南

基于项目的 `spec-template.md`，详细说明如何填写每个章节。

---

## 模板结构概览

```markdown
# 功能规范: [功能名称]

**分支**: `[xxx-功能名称]` | **日期**: [YYYY-MM-DD] | **状态**: 草稿

## 概述
## 用户故事
## 边界情况
## 功能需求
## 成功指标
```

---

## 章节详解

### 1. 标题和元信息

```markdown
# 功能规范: [功能名称]

**分支**: `feature-user-auth` | **日期**: 2026-01-23 | **状态**: 草稿
```

**填写规范**:
- **功能名称**: 简洁描述，3-6 个字（如："用户认证"、"订单支付"）
- **分支**: Git 分支名，格式 `feature-xxx`
- **日期**: 创建日期，格式 YYYY-MM-DD
- **状态**: 草稿 | 审核中 | 已批准 | 实现中 | 已完成

**从 PRD 提取**:
- 查找 PRD 标题或第一章节
- 提取核心功能词汇
- 去除冗余修饰词

---

### 2. 概述

```markdown
## 概述

[一句话描述功能价值和目标用户]
```

**填写要求**:
- **长度**: 1-2 句话，不超过 50 字
- **格式**: "为 [目标用户] 提供 [核心功能]，以便 [价值/目标]"
- **重点**: 价值优先，不要技术细节

**示例**:

✅ **好的写法**:
```
为用户提供邮箱和第三方登录功能，实现快速注册和安全认证。
```

❌ **不好的写法**:
```
本功能使用 OAuth 2.0 协议，支持 JWT token 认证，
数据库采用 PostgreSQL 存储用户信息...（过于技术化）
```

**从 PRD 提取**:
- 查找"背景"、"目标"、"问题陈述"章节
- 提取核心价值主张
- 改写为简洁表述

---

### 3. 用户故事

```markdown
## 用户故事

### US1: [标题] (P1) 🎯 MVP

**场景**: 作为[角色]，我想要[操作]，以便[价值]

**验收**:
- [ ] 当 [条件] 时，[预期结果]
- [ ] 当 [条件] 时，[预期结果]
```

**填写规范**:

#### 标题命名
- 格式: 动词 + 名词（如："邮箱登录"、"密码重置"）
- 长度: 2-5 个字

#### 优先级 (P1/P2/P3)
- **P1**: 核心功能，必须实现
- **P2**: 重要但非关键
- **P3**: 增强功能，可后续迭代

#### MVP 标记 🎯
- 只标记最小可行产品必需的故事
- 通常 2-3 个 P1 故事为 MVP

#### 场景描述
- **角色**: 具体用户类型（如："新用户"、"已注册用户"）
- **操作**: 明确动作（如："输入邮箱和密码登录"）
- **价值**: 用户收益（如："快速访问个人账户"）

#### 验收标准
- 使用"当...时，..."格式
- 每个故事 2-4 个验收条件
- 必须可验证、可测试

**示例**:

```markdown
### US1: 邮箱登录 (P1) 🎯 MVP

**场景**: 作为已注册用户，我想要使用邮箱和密码登录，以便快速访问我的账户

**验收**:
- [ ] 当输入正确的邮箱和密码时，成功登录并跳转到首页
- [ ] 当输入错误的密码时，显示"密码错误"提示
- [ ] 当输入未注册的邮箱时，显示"账户不存在"提示
- [ ] 当连续 5 次输入错误密码时，账户锁定 15 分钟
```

**从 PRD 提取**:
1. 查找"用户故事"、"功能列表"章节
2. 识别 "As a... I want... So that..." 模式
3. 提取或改写为标准格式
4. 补充验收标准（如 PRD 中缺失）

---

### 4. 边界情况

```markdown
## 边界情况

- [ ] 当 [异常情况] 时？
- [ ] 当 [边界条件] 时？
```

**填写要求**:
- 列出 3-5 个边界/异常场景
- 使用问句形式，促使思考
- 覆盖：异常输入、网络异常、并发冲突

**常见边界情况模板**:

```markdown
## 边界情况

- [ ] 当网络请求超时时？
- [ ] 当用户重复提交时？
- [ ] 当输入特殊字符时？
- [ ] 当并发修改同一数据时？
- [ ] 当系统升级维护时？
```

**从 PRD 提取**:
- PRD 通常不完整，需要主动推导
- 查找"异常处理"、"错误场景"章节
- 根据功能特点补充常见边界情况

**推导逻辑**:
```
功能类型 → 常见边界情况

登录/认证 → 密码错误、账户锁定、Session 过期
支付/交易 → 余额不足、重复支付、支付超时
文件上传 → 文件过大、格式错误、存储满
搜索/查询 → 无结果、超时、特殊字符注入
```

### 5. 功能需求

```markdown
## 功能需求

**必须 (MUST)**:
- FR-001: [核心功能]
- FR-002: [核心功能]

**应该 (SHOULD)**:
- FR-003: [重要功能]

**可选 (MAY)**:
- FR-004: [增强功能]
```

**填写规范**:

#### 编号规则
- 格式: FR-XXX（Functional Requirement）
- 从 001 开始递增
- 按优先级排序

#### 优先级分类（MoSCoW 方法）

**MUST（必须）**:
- 核心功能，缺少则产品无法使用
- 通常对应 P1 用户故事
- 示例: "用户必须能够登录"

**SHOULD（应该）**:
- 重要但非关键
- 缺少会影响体验但不阻塞发布
- 示例: "用户应该能够修改密码"

**MAY（可选）**:
- 增强功能，锦上添花
- 可后续迭代实现
- 示例: "用户可以设置安全问题"

#### 描述规范
- 使用主动语态
- 明确主体（用户/系统）
- 可量化、可验证

**示例**:

```markdown
## 功能需求

**必须 (MUST)**:
- FR-001: 用户可以使用邮箱和密码登录
- FR-002: 系统必须在 2 秒内响应登录请求
- FR-003: 连续 5 次登录失败后锁定账户 15 分钟

**应该 (SHOULD)**:
- FR-004: 用户可以选择"记住我"保持登录状态
- FR-005: 系统应该记录所有登录尝试日志

**可选 (MAY)**:
- FR-006: 用户可以使用 Google/GitHub 第三方登录
- FR-007: 用户可以启用双因素认证 (2FA)
```

**从 PRD 提取**:
1. 查找"功能需求"、"需求列表"章节
2. 识别编号需求（REQ-XXX, FR-XXX）
3. 提取或改写为 MUST/SHOULD/MAY 分类
4. 补充遗漏的核心需求

### 6. 成功指标

```markdown
## 成功指标

| 指标 | 目标值 |
|------|--------|
| [用户价值指标] | [如: 用户能顺利完成核心操作] |
| [业务目标指标] | [如: 提升用户体验满意度] |
```

**填写要求**:
- 2-3 个业务导向的指标
- 关注用户价值和业务目标，而非技术指标
- 描述性指标优于量化指标
- **避免**: 具体的技术性能指标（如响应时间、并发数、点击率）

**指标类型（按优先级）**:

| 优先级 | 类型 | 示例 |
|--------|------|------|
| **高** | 用户价值 | 用户能够顺利完成核心操作 |
| **高** | 业务目标 | 提升用户满意度和体验 |
| **中** | 功能完整性 | 所有核心功能正常可用 |
| **低** | 用户行为 | 用户能够理解和使用功能 |
| **❌ 避免** | 技术性能 | ~~响应时间 < 500ms~~ |
| **❌ 避免** | 数据指标 | ~~转化率 > 60%~~ |

**示例**:

✅ **好的写法**（业务导向）:

```markdown
## 成功指标

| 指标 | 目标值 |
|------|--------|
| 用户认证体验 | 用户能够顺利完成登录和注册 |
| 账户安全保障 | 用户密码安全存储，支持密码重置 |
| 功能完整性 | 核心认证功能全部可用 |
```

❌ **不好的写法**（技术导向）:

```markdown
## 成功指标

| 指标 | 目标值 |
|------|--------|
| 登录完成时间 | 用户 30 秒内完成登录 |
| 登录成功率 | > 98%（排除密码错误） |
| 接口响应时间 | P95 < 500ms |
| 并发支持 | 支持 1000 并发登录请求 |
```

**为什么避免技术指标？**

1. **Spec 阶段关注"做什么"，不是"怎么做"**
   - 技术指标属于实现阶段（Plan/Task）
   - Spec 应聚焦用户价值和业务目标

2. **技术指标会限制设计空间**
   - 过早约束可能导致次优方案
   - 应在技术设计阶段确定性能要求

3. **业务指标更稳定**
   - 技术指标会随技术栈变化
   - 业务目标长期不变

**从 PRD 提取**:
- 查找"成功标准"、"业务目标"章节
- 提取业务导向的指标
- **转换技术指标为业务指标**（如有）:
  - "响应时间 < 500ms" → "用户体验流畅，无明显延迟"
  - "登录成功率 > 98%" → "用户能够顺利完成登录"
  - "并发 1000" → "系统支持多用户同时使用"

## 完整示例

```markdown
# 功能规范: 用户认证

**分支**: `feature-user-auth` | **日期**: 2026-01-23 | **状态**: 草稿

## 概述

为用户提供邮箱和第三方登录功能，实现快速注册和安全认证。

---

## 用户故事

### US1: 邮箱登录 (P1) 🎯 MVP

**场景**: 作为已注册用户，我想要使用邮箱和密码登录，以便快速访问我的账户

**验收**:
- [ ] 当输入正确的邮箱和密码时，成功登录并跳转到首页
- [ ] 当输入错误的密码时，显示"密码错误"提示
- [ ] 当连续 5 次输入错误密码时，账户锁定 15 分钟

---

### US2: 邮箱注册 (P1) 🎯 MVP

**场景**: 作为新用户，我想要使用邮箱注册账户，以便使用产品功能

**验收**:
- [ ] 当输入有效邮箱和密码时，创建账户并发送验证邮件
- [ ] 当使用已注册邮箱时，显示"邮箱已存在"提示
- [ ] 当密码强度不足时，显示密码要求提示

---

### US3: 密码重置 (P2)

**场景**: 作为忘记密码的用户，我想要重置密码，以便重新访问账户

**验收**:
- [ ] 当输入注册邮箱时，收到重置密码链接
- [ ] 当点击链接时，跳转到密码重置页面
- [ ] 当设置新密码后，可以使用新密码登录

---

## 边界情况

- [ ] 当网络请求超时时，如何提示用户？
- [ ] 当用户重复点击登录按钮时，如何防止重复请求？
- [ ] 当邮箱验证链接过期时，如何处理？
- [ ] 当并发登录同一账户时，Session 如何管理？

---

## 功能需求

**必须 (MUST)**:
- FR-001: 用户可以使用邮箱和密码登录
- FR-002: 用户可以使用邮箱注册新账户
- FR-003: 系统必须在 2 秒内响应登录请求
- FR-004: 密码必须加密存储（BCrypt）

**应该 (SHOULD)**:
- FR-005: 用户可以重置忘记的密码
- FR-006: 系统应该记录所有登录尝试日志
- FR-007: 用户可以选择"记住我"保持登录状态

**可选 (MAY)**:
- FR-008: 用户可以使用 Google OAuth 登录
- FR-009: 用户可以启用双因素认证 (2FA)

---

## 成功指标

| 指标 | 目标值 |
|------|--------|
| 注册完成时间 | 用户 2 分钟内完成注册 |
| 登录完成时间 | 用户 30 秒内完成登录 |
| 登录成功率 | > 98%（排除密码错误） |
| 接口响应时间 | P95 < 500ms |
```

## PRD 到 Spec 映射表

| PRD 章节 | Spec 章节 | 转换方法 |
|---------|----------|---------|
| 问题背景/目标 | 概述 | 提炼为一句话价值主张 |
| 用户故事 | 用户故事 | 直接映射，补充验收标准 |
| 功能列表 | 功能需求 | 分类为 MUST/SHOULD/MAY |
| 验收标准 | 验收标准 | 整合到用户故事中 |
| 成功指标/KPI | 成功指标 | 提取可量化指标 |
| 异常处理 | 边界情况 | 改写为问句形式 |
| 技术方案 | ❌ 不包含 | Spec 阶段不涉及技术细节 |

## 常见错误

### ❌ 错误 1: 概述过于详细

```markdown
## 概述

本系统采用前后端分离架构，后端使用 Node.js + Express 框架，
数据库使用 PostgreSQL，前端使用 React + TypeScript...
```

**问题**: 技术细节属于设计阶段，不属于 spec

**正确**:
```markdown
## 概述

为用户提供邮箱登录和注册功能，支持密码重置和账户安全管理。
```

### ❌ 错误 2: 验收标准不可验证

```markdown
**验收**:
- [ ] 登录功能正常
- [ ] 用户体验良好
```

**问题**: "正常"、"良好"无法量化

**正确**:
```markdown
**验收**:
- [ ] 当输入正确凭据时，2 秒内跳转到首页
- [ ] 当输入错误密码时，显示明确的错误提示
```

### ❌ 错误 3: 功能需求描述模糊

```markdown
- FR-001: 系统支持登录
```

**问题**: 不明确支持哪种登录方式

**正确**:
```markdown
- FR-001: 用户可以使用邮箱和密码登录
- FR-002: 用户可以使用 Google OAuth 登录（可选）
```

## 快速检查清单

生成 spec 后，检查以下项：

- [ ] **文件名**: 英文 kebab-case 格式（如 `user-authentication.md`）
- [ ] **标题**: 功能名称简洁明确
- [ ] **概述**: 一句话说清楚价值（< 50 字）
- [ ] **用户故事**: 至少 1 个 MVP 故事，有验收标准
- [ ] **边界情况**: 列出 3+ 个异常场景
- [ ] **功能需求**: 区分 MUST/SHOULD/MAY
- [ ] **成功指标**: 业务导向（非技术指标）
- [ ] **优先级**: P1 故事标记 🎯 MVP

---

## 总结

**核心原则**:
1. **简洁优先**: Spec 是理解需求的文档，不是技术设计
2. **价值驱动**: 关注用户价值，而非技术实现
3. **可验证**: 所有需求和标准必须可测试
4. **优先级明确**: 清晰区分 MVP 和增强功能
